## Kernel assembly: Git hosting (T-166–T-170)

`kodama server --assembly kernel` (ADR 0013, O-36) is a separate composition from the core assembly below: it runs over the current 16-table product schema and hosts Git itself. This section states exactly what is wired and what is not; package existence still does not mean a route is served. The kernel's own routes (projects, pipelines, runs, secrets, artifacts, tasks) are recorded in the [phase 3 handoff](simplification-phase-3.md).

**Wired and unit-verified.**

- **Repositories.** `/api/v1/tenants/{tenant}/repositories` (the tenant knowledge base, `context`) and `/api/v1/tenants/{tenant}/projects/{project}/repositories`: create, list, read, change default branch or policy (`If-Match`), archive, restore and read refs; authorization is the caller's current role on every call. The published description is [api/kernel-git.yaml](../../api/kernel-git.yaml), assembled into [api/openapi.yaml](../../api/openapi.yaml) and the generated client.
- **Credentials.** `POST /api/v1/tenants/{tenant}/git-credentials` exchanges the caller's access token for a human or single-use seed credential (HTTP Basic password, stored only as a hash, shown once). A seed needs the literal `engineer` role (`kodama seed --role admin --role engineer`); run and integration credentials are issued to runs by the kernel, never over the API.
- **Transport.** `/git/<tenant>/<project>/<repository>.git` streams the smart HTTP protocol to the tenant's worker under a short-lived signed forwarding assertion; the caller's credential never reaches the worker. It is not a JSON route and is described in prose in the API document. The worker's control routes (`/internal/git/v1/tenants/{tenantId}/…`) authenticate with a tenant-bound worker identity and are not public.
- **Hosting by environment.** `development` hosts one in-process worker per tenant on a data root below `KODAMA_STATE_DIR` and needs no Git credential, worker address, control token or key file (`Test_unit_kernel_git_development_hosting`). Any other environment forwards to `KODAMA_GIT_WORKER_URL` (a `{tenantId}` template) with `KODAMA_GIT_CONTROL_TOKEN` and the two signing key files; `production` refuses the in-process worker. The `test` environment's one-container-per-tenant profile (`DEV_GIT=native`, `devctl git-worker`) is wired in `dev/` and covered by unit tests against a fake engine; see the [development runbook](../../dev/README.md#kernel-git-hosting).
- **Push to run.** A receive is one `git.refs_updated` event (applied updates inline) in `audit_events`, drained by the outbox publisher to an in-process or NATS JetStream bus; the dispatcher reads `.kodama/*.yaml` from the worker at the exact pushed commit, indexes the pipelines, matches triggers and admits runs pinned to that commit, once per event and ref. A refused push changes and records nothing.
- **Run sources.** A run checks out its pinned source at the recorded commit, reads the tenant and project `context` repositories read-only, and uses a run-scoped credential kept outside `/workspace` that ends with the run.
- **Bootstrap.** The documented example in the [development runbook](../../dev/README.md#bootstrap-example-project-repository-seed-push-pipeline-run) (create project, create repository, request a seed, `git push`, pipeline indexed, run admitted) is automated in memory with the real Git client by `Test_unit_kernel_git_bootstrap_roundtrip`.

**Verification boundary.** The checks are unit and in-process: in-memory and PostgreSQL-backed stores (the latter skip without a database), the real `git` binary, a fake container engine for the scope tooling. The real-PostgreSQL smoke of create → seed → push → index → run, the Podman and Docker runs of the `test` profile, and the full end-to-end acceptance run on `main` after the merge; nothing here is recorded as having run there.

**Not wired or not qualified.** Kubernetes installation of the per-tenant workers (T-156/T-157) and the production profile; stage acceptance (T-133); backup, restore and offboarding of tenant Git volumes; managed-agent and MCP Git tools; full `kodactl` coverage of the routes above; provider import; TLS on the `test` profile's workers; host-run servers against the `test` profile's per-tenant containers (the `{tenantId}` template resolves container names on the scope network). The published API document describes the kernel Git routes; the core assembly below does not serve them and answers 404. No production, hosted or stage qualification is claimed.

### Kubernetes stage composition (implemented, receipt pending)

`deploy/charts/kodama-kernel` runs this kernel assembly on Kubernetes. The
server uses a cloud KMS provider at startup (Scaleway Key Manager,
AWS KMS or GCP Cloud KMS) and a strict `kube.json` tenant map. Each run creates a
ReadWriteOnce workspace claim, a checkout Job in the tenant namespace and one
restricted Job per step; the step Jobs mount the same claim and only the
declared secret files. `/readyz` pings PostgreSQL; a running step is cancelled
from a committed `cancel_requested_at`; the startup loop adopts every
`running` run by its deterministic Job names.

For this disposable test stage the native Git workers run in-process on the
server's retained volume under the explicit O-37 acknowledgement. The
`test/e2e/kube-kernel` suite (five named readiness checks) covers clean install,
database outage, shared workspace/logs, tenant denial, native Git seed push and
trigger, run-scoped publication, KMS-backed secrets across restart, cancellation
and adoption. The live stage receipt is not yet recorded.

## Core assembly (T-070)

The first executable slice of the product. `internal/app` explicitly constructs the identity authority (standalone profile, OIDC bearer tokens), the tenant stores over the non-owner PostgreSQL role, the declared migrations, the HTTP routes below, the event workers and the T-062 runtime-enabled execution store; nothing is registered implicitly and a missing binding fails startup or fails closed. It is selected with `--assembly core` (or `KODAMA_ASSEMBLY=core`). `kodama server` without it stays the health-only scaffold: the default has not been switched to the core assembly, so a binary is never mistaken for a complete factory.

**Served** under `/api/v1` (the aggregate document is [api/openapi.yaml](../../api/openapi.yaml), generated from the module fragments): identity, projects and memberships; work items; project variables and secrets (write-only values); pipeline definitions (container steps; agent and gate steps from T-072, below); workspaces (real Git); run admission, reads, steps and cancellation with `Idempotency-Key`; artifact metadata; project and run event streams (SSE with `Last-Event-ID`). `/healthz` is liveness; `/readyz` is ready only while PostgreSQL (with the migrated schema), JetStream, S3 and the OIDC issuer answer and every worker runs.

**Workers**, started and stopped deliberately: event publisher (outbox → JetStream), the work-cancellation consumer (inbox, durable), and periodic repair — event repair, replay resume and retention pruning; run reconciliation (cancelled-work scan, **retained source reference redrive**, observation, termination, redrive of unconfirmed starts and removal of settled workloads); workspace reconciliation; artifact orphan cleanup; and, from T-071, the dispatch loop (below).

**Not wired** (fail closed, never an allow-all fake): ChatOps until the installation selects it (T-075, below), cloud KMS (only the explicit development keyfile outside production), hosted identity. Agent profiles, human gates and delivery arrive with the manual agent/delivery assembly (T-072, below); the model gateway and MCP proxy with the M2 composition (T-039, below) when the installation selects them; the native Git trigger's production persistence and admission with T-038.

### Run it

```sh
kodama migrate                      # owner identity; applies the declared order, grants the runtime role
kodama bootstrap --tenant-id t_acme --tenant-key acme --display-name Acme \
  --operator-id op_1 --eligible-subject '<oidc subject>' --token-file admin.token   # once per installation
kodama server --assembly core       # serves, starts the workers, drains on SIGTERM
```

Configuration is environment plus the secrets directory (`KODAMA_SECRETS_DIR`, default `/secrets`) and the version-2 document selected by `KODAMA_CONFIG_FILE`. The document's `secrets.adapter` selects `keyfile` or `kms`; KMS cloud names are `aws`, `gcp`, `scw`. Environment-only test startup uses `KODAMA_SECRETS_ADAPTER=keyfile`; `KODAMA_SECRETS_CONFIG` replaces the entire secrets object as JSON. The old `KODAMA_KMS_*` names require migration. See [secrets configuration](../../deploy/charts/kodama/README.md#kms-selection) for key mappings, credential mounts and rotation. Secret files include database URLs, S3 keys, NATS/Git tokens, cursor/idempotency keys and optional `git-credentials.json`; production uses cloud KMS. The full settings list is in `LoadCoreConfig` ([internal/app/core_config.go](../../internal/app/core_config.go)). T-105 completes startup wiring; T-104 owns live Kubernetes/KMS acceptance and T-029 full recovery.

`KODAMA_CONFIG_FILE` names an optional settings document (the chart's `config.yaml`, see [Chart join](#chart-join-t-027)) that supplies defaults for the settings above and the Kubernetes execution policy; a variable that is set wins. `kodama migrate` accepts `KODAMA_DATABASE_RUNTIME_ROLE` (the runtime role's name) instead of `database-runtime-url`, so a migration Pod need not hold the runtime credential. `KODAMA_ENV` is required by the core assembly (below). The serving database role must not own the schema, be a superuser or bypass row level security; startup refuses it. A project's repository is configured in its settings (`settings.repository`: `id`, `url`, `baseRef`, `checkoutSecretRef`, `publisherSecretRef`); the referenced `secret://installation/<name>` credentials come from `git-credentials.json` and are bound to an https URL prefix (same scheme, exact host and port, then a path boundary: `https://git.example` never covers `https://git.example.evil`, `/repo` never covers `/repository`) and a tenant list, so a project cannot aim a credential at another host.

### Commands

`kodama context …`, `auth login|logout`, `work create|get|list|update|history|transition`, `workspace …`, `pipeline validate|register|get|list`, `run start|get|list|steps|cancel|watch`, `variable …`, `secret …`. `run logs` reads the bounded log of one attempt. From T-072 the `agent` (profiles), `gate`, `environment` and `deployment` groups are offered too; nothing for the model gateway, MCP, webhooks or ChatOps is (model settings and MCP registrations of the M2 composition are administered through the HTTP API and the generated client). `KODAMA_CONTEXT_FILE`, `KODAMA_CREDENTIAL_DIR` and `KODAMA_ALLOW_INSECURE_LOOPBACK=true` (development only) adjust local client state.

## Container execution assembly (T-071)

`kodama server --assembly core` also composes the path from a committed run to a container and back: the dispatch loop, the runtime selected by the environment, the runtime API the step entrypoint calls, the result and source routes over guarded stores, and the log API. It is assembled by `AssembleExecution` in `internal/app/execution.go`, a pure composition over injected adapters, so its constructor selection, worker lifecycle and guard bindings are unit-tested with no service.

**Environment (`KODAMA_ENV`, SD-12).** Required, no default, matched exactly: `development`, `test` or `production`. An unset or unknown value stops startup before any setting is read. `internal/app` is the only package that reads it; the table of adapters per port is `Selections` and the executable one is `Constructors` (`internal/app/constructors.go`).

| Port | `development` | `test` | `production` |
| --- | --- | --- | --- |
| Runtime | Process | Podman | Kubernetes |
| Key wrapper | ephemeral (development composition) | local keyfile | cloud KMS (not wired here: refused, never the keyfile) |
| Verifier | static, seeded (development composition) | OIDC fixture | standalone OIDC over https |
| Persistence, events, objects, source | memory adapters (development composition) | PostgreSQL, JetStream, S3, Git | PostgreSQL, JetStream, S3, Git |

`production` refuses each development or test adapter at construction: the in-memory store (`memdb`, the memory stores, anything flagged `DevelopmentOnly`), the Process and Podman runtimes (also behind a decorator, by their backend identity; production runs workloads on Kubernetes only), the development KEK (the keyfile provider, the ephemeral wrapper), and the OIDC and S3 fixtures (an issuer, or an object store endpoint, that is not https, whatever `…_ALLOW_INSECURE_HTTP` says). `kodama bootstrap` requires `KODAMA_ENV` too and builds its verifier through the same constructor, so production refuses the OIDC fixture and an unset or unknown environment stops it before any connection or token verification. `NewCore` composes `test` and `production` over real services and refuses `development`, whose memory composition is the development composition below (T-027); it never substitutes memory for a missing service. The in-workload `kodama step` and the CLI read no environment selection.

**Runtime API** under `/runtime/v1/attempts/{attemptId}`: `admit`, `token` and `context` (runtime authority, verified through the selected backend's Job observer), `result` and `source` (guarded), and the artifact `reserve` and `complete` routes (runtime-token authenticator, deny-by-default authorizer). `secrets/resolve` is wired when the installation supplies the secret route (`SecretRoute`, T-097/T-101), but it resolves **only credentials named by a pinned deployment environment's retained snapshot**; an attempt with no environment pin resolves nothing (403), and the registration check admits `secretFiles` only (an ENV `secretRef` is refused). Direct project-secret delivery to an ordinary step is therefore not implemented ([T-107](../tasks/T-107-direct-secret-delivery.md)); the T-104 Kubernetes qualification used environment-bound delivery. Without the route the operation answers `not_found` (listed in `ExecutionSlice.Disabled`). Source proposals scan new objects for the attempt's injected values through `attemptNeedles`, which reads the attempt's pinned context from the execution store: an attempt that declares no secret and no deployment environment has an empty needle set and can publish; one that declares either is refused as unavailable (its injected values cannot be enumerated until secret delivery is bound), and an attempt that cannot be established is never treated as an empty set. The signing key is a PEM P-256 key (`KODAMA_RUNTIME_KEY_FILE`, default `runtime-signing-key` in the secrets directory) at an explicit generation (`KODAMA_RUNTIME_KEY_GENERATION`).

**Guards (T-062).** Two execution services run over the same runtime: the trusted one (dispatch, cancellation, observation, reconciliation, over the plain store) and the guarded one, which only the result path uses and whose store repeats the runtime session check inside the run's transaction. The assembly refuses to start if both are the same store, or if the Job observer is not the selected runtime's. Workspace publication on `source` uses a second workspace service over the guarded workspace store. A missing limit, authority, runtime or observer denies; a runtime that lacks a guarantee the policy requires (image, isolation, resource limits) refuses admission. Only `development` drops that requirement, for its host-process fixture.

**Workers** (`ExecutionSlice.Workers`): the dispatch loop (`DispatchInterval`, bounded per tenant per pass; every start is a committed claim followed by a runtime call outside any transaction, and a lost start is redriven with the same attempt and workload identity by the reconciler) and the runtime's own loops (the Kubernetes reconciler). Shutdown order: readiness drains, HTTP stops, workers stop and are awaited, then the runtime's resources, the pools and the broker close; a started workload keeps running and the next process adopts it. A settled workload is removed only after its log was observed (and, on Kubernetes, collected by the controller fallback), so removal waits on a capture still in progress and proceeds on explicit unavailable evidence.

**Logs.** `GET /api/v1/tenants/{t}/projects/{p}/runs/{id}/logs` (`run:read` at the route, then `run:read` and `evidence:read` in the module on every call). Live reads exist on Kubernetes only (the module's reader and the policy's namespace); on Podman and Process, retained logs uploaded by the entrypoint are served and live reads are refused. Known-secret redaction is not configured because no secret is delivered yet.

**Settings** (in addition to the core ones): `KODAMA_ENV`; `KODAMA_RUNTIME_URL` (the origin workloads call back; https, plain http only for loopback outside production), `KODAMA_RUNTIME_CA_FILE`; test: `KODAMA_RUNTIME_STATE_DIR`, `KODAMA_ENTRYPOINT_BINARY` (a static Linux `kodama` mounted into the step's image), `KODAMA_PODMAN_BINARY/_NETWORK/_CPUS/_MEMORY/_PIDS`; production: `KODAMA_KUBE_API`, `KODAMA_KUBE_TOKEN_FILE` and `KODAMA_KUBE_CA_FILE` (default in-cluster paths), `KODAMA_KUBE_POLICY_FILE` (the JSON of `kube.PolicyConfig`: tenant targets, digest-pinned injector image, callback origin and egress, resource bounds). Podman and Process refuse an attempt that consumes workspace source (checkout there is not supported yet); Kubernetes issues the read-only checkout credential from the project's repository configuration.

Migration order gains the log capture records last. The installed Podman and kind round trips, cancel/restart and result-guard checks against real services are T-026's; the integration tests of the core assembly need `KODAMA_ENV=test` and the runtime settings above before they run again.

## Manual agent, review and delivery assembly (T-072)

`kodama server --assembly core` also composes the manual-trigger path from a run to a reviewed, deployable candidate: agent profiles, the agent step kind, canonical human gates, environments and deployment records with their runtime callbacks, and deployment-bound cleanup. Two pure compositions over injected adapters carry it (`internal/app/delivery.go`), so constructor and authority selection, gate progression, the worker lifecycle and delivery routing are unit-tested with no service: `BindDelivery` builds the delivery-owned ports of the execution dependencies, and `AssembleDelivery` registers the human routes and the workers. Doubles are injected only by tests; `NewCore` selects the PostgreSQL-backed adapters, and `production` refuses each development or test one at construction.

**Execution dependencies (replaces the M1 unbound note).** `execution.Dependencies` now carries the deployment-bound cleanup authorization (`Cleanup`, recorded and cleanup-requested deployment of the scope only) and the delivery **effect reconciler**, so an apply whose answer was lost resolves from its deployment record instead of staying blocked. The reconciler speaks only for steps that implement the delivery scripts' replay protocol, established by an explicit installation qualification of the step's own frozen image and entrypoint (`ToolQualification`: protocol `apply` or `cleanup`, digest-pinned image, exact command; `delivery-tools.json` in the secrets directory or `KODAMA_DELIVERY_TOOLS_FILE`, strict JSON, empty by default). An apply step must also declare an environment; a cleanup-run step must match a `cleanup` qualification, so an unrelated step of a cleanup run is not covered by the deployment's cleanup request. Every other step, including an arbitrary command that merely declares an environment, stays "still unknown" and blocked, never replayed on the strength of a missing record; without qualifications nothing is resolved from a record. The environment resolver and the cleanup environment are bound only when the execution store binds environments inside its admission transaction, which needs a transaction-bound delivery reader no production adapter supplies yet (a bounded prerequisite of T-067/T-077's qualified join): until then execution itself refuses an environment-declaring admission (`step-environments` in `Routes.Disabled`).

**Served** under `/api/v1` (aggregate and client regenerated): `agent-profiles` (`run:read` / `run:manage`), `gates` list/read (`evidence:read`) and `gates/{id}/decisions` (`gate:decide`, keyed and idempotent), `environments` and `deployments` including `deployments/{id}/cleanup` (`run:read` / `deployment:manage`). The deployment callbacks (`deployment.call`) are served on the runtime API under `/runtime/v1/attempts/{attemptId}/deployments`; the route only checks a verified runtime principal and the delivery service authenticates the grant itself. Pipeline definitions now accept container, agent and gate steps; an environment reference must exist in the project and be readable by the registering user.

**Gates** wait in durable records and consume no compute: the gate reconciler (`gate-reconciler`, every `ReconcileInterval`) requests the gate of a ready gate step, a human decision is recorded without progressing anything, and the step transition is applied once from the durable decision (also woken by the `gates-decision` consumer; a missed event is covered by the scan). A revoked reviewer's approval is not consumed. Deployment-bearing gates fail closed (no transaction-bound deployment reader exists in production, `deployment-gates`), and a gate that needs conformance evidence is not created (the report output name is agreed with the wrapper in T-031, `agent-candidate-gates`).

**Agents** are selected as one chain (`agents/adapters.Chain`: the expanding store, the keyed creator, the planner decoration and the step kinds together, `Decorated` over the gate-aware store). The profile service gets a compatibility catalogue that qualifies nothing and approvals that approve no model or tool until a wrapper image, the model gateway and the MCP proxy are selected for an installation (T-031, T-085; they need a provider endpoint and a destination policy no configuration carries yet), so registration refuses and no agent step can be admitted (`agent-steps`, `model-gateway`, `mcp-proxy`). Tests use deterministic profile fixtures and scripted results; live provider and wrapper smoke is T-085's.

**Cleanup** (`deployment-cleanup` worker, T-066/T-092): every sweep lists the projects of the installation, requests cleanup of settled deployments past their `expires_at` and admits one cleanup run per round from the project's cleanup definition, the newest registered version of the pipeline named `kodama-cleanup`, which declares the string input `deployment_id`. Admission rechecks the record owner's authorization; duplicate claims converge on one run; an unusable or missing definition is reported and retried. The sweep interval is `Tuning.CleanupSweep`.

**Workers** added to the group: `gate-reconciler`, `deployment-cleanup` and `event-consumer:gates-decision`. **Migrations** gain `agents`, `delivery` and `gates` last. The runtime action ceiling of a step that calls the delivery callbacks must include `deployment.call` (operator policy). Real-path checks (`agent_delivery_assembly`, `gate_consumption_atomicity`, `delivery_assembly_replay`) and the Podman/kind checkpoint are T-038's; the native Git trigger and the model/tool slices are joined by T-039, below.

## M2 composition: model gateway, MCP proxy and Git push trigger (T-039)

T-039 merges the runtime, gateway, gate and delivery contributions into the one server and CLI. What it adds on top of T-072 is three pure compositions over injected adapters (`internal/app/modeltools.go`, `triggers.go`), so route and capability registration, authority at each seam, the production construction guard and worker lifecycles are unit-tested with deterministic provider and tool responses, no container and no service. `NewCore` selects the PostgreSQL-backed adapters of the model gateway and MCP proxy (`modeltools_core.go`); `production` refuses each development or test adapter at construction.

**Installation statement (`model-tools.json`).** Strict JSON in the secrets directory (or `KODAMA_MODEL_TOOLS_FILE`), empty by default: the approved provider origins and path prefixes with the per-model token accounting the gateway estimates with, optional private trust roots and provider networks (loopback and the whole address space are refused under `production`), the approved MCP hosts, and the **wrapper catalogue**: the exact image/wrapper/harness tuples with mandatory compatibility evidence. The gateway and the MCP proxy are selected **together**; absent the file nothing is approved, no agent profile can register and no agent step can be admitted (`agent-steps`, `model-gateway` and `mcp-proxy` stay in `Routes.Disabled`). A catalogue without a gateway, an unknown control, an unpinned image or a duplicate tuple stops startup. The catalogue is installation evidence: it is not populated here, and live-provider/wrapper-image qualification is T-085.

**Served** (when selected). Under `/api/v1`, in the aggregate and the generated client: `GET|PUT …/model-settings` (`config:read` / `project:settings`, `If-Match` versioned) and `GET|POST …/mcp-servers`, `PATCH|DELETE …/mcp-servers/{id}` (`project:read` / `project:settings`, the module also asks `credential:manage`). Beside the API, authenticated by the attempt's runtime token alone and not part of the public document: `POST /gateway/v1/attempts/{id}/chat/completions` (streaming chat completions) and the Streamable HTTP endpoint `/internal/mcp/v1/attempts/{id}/servers/{registration}`. Profile registration is approved by what the project stored: a model must be the enabled settings' model on the settings' exact endpoint, a tool a qualified `<registration>/<tool>` the registration enables (no bare names, no wildcards); withdrawing the settings withdraws the approval. **Workers**: `model-gateway-reconciler` (abandoned requests: unsent are released uncharged, forwarding ones become unknown and keep the run's slot) and `mcp-proxy-sweeper` (stale tool calls are recovered as unknown, never replayed). **Migrations** gain `gateway` and `mcpproxy` last.

**Native Git push trigger (O-03).** `AssembleTriggers` mounts the signature-authenticated hook `POST /api/v1/git-hooks/{triggerId}` beside the public router (behind a flood throttle per connection peer, which behind a proxy is the proxy; it is not authentication). `TriggerAuthorizer` decides with current identity state: installing needs `project:settings`, and every delivery re-checks that the installing principal still holds `run:manage`: the role matrix keeps those two apart, so an installer needs both grants. The trigger store, the hook secret and definition lookup, and the exact-commit admission ledger (`StartRun`/`FindRun`/`DecideRefusal` over one admission store) have no production adapter yet: **`NewCore` leaves the route unregistered and reports `git-webhooks` as disabled**; the unit composition uses the module's in-memory store, the real project repository binding and the real local Git reader, so the exact commit is proved against an actual repository. T-038 owns `native_hook_roundtrip` with real Git and durable admission. Trigger installation is a Go-level seam (`TriggerSlice.Service`); the HTTP exposure of installation is not specified yet.

**Contract.** The public document adds the model-settings and MCP-server operations only (version 0.2.0); the workload streams and the hook stay out of it and out of the generated client (their schemas are pruned from the aggregate). `make test-m2` runs `TestM2CompositionSmoke` (`m2_composition_smoke`) and `TestM2ContractCompatibility` (`m2_contract_compatibility`) under `KODAMA_ENV=development`: the latter checks the aggregate against the committed client-visible baseline of the pre-M2 document (`internal/app/testdata/api-baseline-t072.json`, from `internal/app/apispec.Summarize`; removed operations, parameters, response statuses, members or enum values, new required parameters or request members are reported), reproducible generation, the M1 client flow on the M2 composition, tolerance of additive response members, and the served payloads against their published schemas. The development composition also enables the agent step kind through the same chain `NewCore` builds (profile service with the M2 catalogue and approvals, expanding store, keyed creator, planner), so `TestM2CompositionSmoke` validates and admits agent definitions against M2-approved profiles (unknown profiles, mutable aliases, forged agent payloads and a withdrawn model approval are refused) and, over the T-072 gate fixture and this composition's delivery slice, shows a gate waiting without compute, progressing once after a valid decision, and refusing stale and revoked decisions. Gate steps themselves still need the gate-aware execution store of the PostgreSQL composition (T-073/T-038).

## Business-loop composition: dependencies, flow summaries, QA mapping and ChatOps (T-075)

**Always selected (production).** The business dependency graph: its baseline tables, its use cases and routes, and the **transaction-bound dependency guard in the work store** (it replaces the M1 explicit "none"), so a `ready → active` transition reads the current links and prerequisite states inside its own transaction. **ChatOps (T-041).** The planner is bound to the event bus as the `chatops` consumer: it records one durable intent per matching destination and event inside the bus's inbox transaction and never calls a receiver; the `chatops-delivery` worker sends only durable intents, outside any transaction, with the stable `Idempotency-Key`. The consumer gets its own JetStream durable (`kodama-chatops`) and inbox repair pass beside the cancellation and gate consumers. ## Development composition (T-027)

The whole M1 slice is also composed under `KODAMA_ENV=development` from the modules' in-memory adapters, the Process runtime and an in-process event bus, with no container and no service (`make test-m1`, about ten seconds). It is test code (`internal/app/development_test.go`) on purpose: the memory adapters live in the modules' `*test` packages and are injected there, never installed as a fallback of the executable constructors, and `production` refuses every adapter it uses (`IsDevelopmentAdapter`, `Admit`). The composition test builds the same wiring under `production` and requires the refusal.

What is shared with the PostgreSQL composition, so the two cannot drift: the router, the authorizer rule table and every route registration (`NewPublicRouter` in `internal/app/public.go`, called by `NewCore` and by the development composition), the execution slice (`AssembleExecution`), the module services and their HTTP handlers. What differs is each module's `MEMORY.md` and `internal/app/memory.go`: the in-process idempotency record (joined to the run admission's memdb transaction, so a refused response or failed commit leaves neither the run nor a replay record; the secrets memory store opens its own unit, so its record is written inside that unit and withdrawn if it does not commit), the keyed run and secret writes, the transaction-bound peers of the memory execution store (identity authority, work admission lock, workspace writer slot and retained-source intent, secret pins, event outbox), the session guard of the result path (the grant check and the mutation share one transaction and the grant must belong to the mutated scope and run), the writer guard of work transitions (an active item cannot leave active while a writer attempt is unsettled), a Git adapter that maps the project's https repository URL to a temporary bare repository, and the observation projection. They model outcomes (committed together or not at all, replayed, refused), not locks, lock order, isolation levels, row-level security or restart persistence; those stay with the PostgreSQL checkpoint (T-026).

The acceptance tests, all in `internal/app`:

- `TestM1CompositionSmoke` (`m1_composition_smoke`): every operation of `api/openapi.yaml` is registered and answers 401 without a credential and for an unknown token, a verified caller without a binding learns nothing about a tenant, operations of the other fragments (gates, agents, delivery, ChatOps, Git webhooks, gateway, MCP) are not served and are recorded as disabled, the runtime API serves the frozen contract's operations (the unwired `resolveSecret` answers `not_found`; a user token is no runtime credential), roles do not exceed their permissions, workers start and stop deliberately, a work-cancellation event travels outbox → in-process broker → consumer inbox → execution and cancels the run, the migration manifest creates every table readiness requires, and the command-line client works against the same API.
- `TestM1ContractConsistency` (`m1_contract_consistency`): the aggregate lists its fragments and secures every operation; every example validates against its schema; the runtime operations in `api/runtime.yaml` are the contract's and are served under its base path; the error envelopes the process answers validate against the public and runtime error schemas; and the events the composed modules emit decode as catalog events with the owning tenant and project. Served successful payloads are validated too: representative public responses (identity, work items, variables, secrets, pipeline definitions, workspaces, runs and their failures) against the response schemas of `api/openapi.yaml`, and an authenticated admit, context, renew, artifact reserve and result exchange of a real dispatched attempt against `contracts/runtime/v1/schema.json`, each with negative controls (a missing, mistyped, undeclared or out-of-enum member fails the check).
- `TestM1GeneratedClient` (`m1_generated_client`): the generated client submits a run, reads its status and steps, replays an idempotent submission (same run, `Idempotent-Replayed: true`, nothing admitted), receives the stable `409 idempotency_conflict` for a conflicting key and body and the stable codes for the other failures, sees the run dispatched to the Process runtime and cancels it; generation from the fragments with the pinned generator reproduces the committed document and client byte for byte.

A step on the Process runtime runs the declared command directly, with no entrypoint, so no workload calls back by itself; the contract test plays the entrypoint's admission, context, renewal, artifact reservation and result calls against a real committed attempt. The attempt authority of the runtime API is a memory stand-in seeded from that attempt, and artifact upload, source publication and workload callbacks over a network stay with T-071's injected-adapter tests and the installed round trip (T-026).
