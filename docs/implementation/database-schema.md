# Database schema

**Implementation of [ADR 0013](../adr/0013-two-layer-architecture-and-domain-simplification.md), including its 2026-10-30 pipeline-runtime amendment.** The current executable baseline has **15 product tables**, plus `git_credentials` from the appended Git hosting contribution, `signal_records` from the pipeline-runtime expand contribution, and `run_commands`, `run_workload_observations` and `run_resource_observations` from the durable run-state contribution, and `run_materializations` from the wait-decision contribution: **21 product tables**. The migration runner's `schema_migrations` ledger is separate. The earlier fixed “14/15-table” promise is withdrawn in favor of this explicit inventory.

The executable schema is [001_schema.sql](../../internal/storage/migrations/001_schema.sql), with runtime privileges in [002_grants.sql](../../internal/storage/migrations/002_grants.sql). The [pipeline-runtime simplification plan](pipeline-runtime-simplification.md) owns the pending removal of `projects.task_workflow` and the task workflow fields. Existing server queries are ported as their replacement owners become executable.

**Appended contribution (O-36, T-167):** [003_git_hosting.sql](../../internal/storage/migrations/003_git_hosting.sql) is the only migration after the baseline. It adds `repositories.policy` (`directPushToDefault`, `integrationPipeline`), `repositories.empty` (the tenant worker's report) and `repositories.journal_ack` (the acknowledged receive-journal sequence), and one table, `git_credentials` (below, 16 product tables in total). No push-record, grant or workspace-association table exists; a receive is one `git.refs_updated` row in `audit_events` and the worker's local journal recovers a lost outcome. The baseline statements above describe `001`/`002`; the sections below name the Git additions where they apply.

**Appended contribution (T-179, P2.1 stages 1–2):** [004_pipeline_runtime_expand.sql](../../internal/storage/migrations/004_pipeline_runtime_expand.sql) expands the schema for the pipeline runtime and validates existing data; it drops nothing. [Expand and validate](#pipeline-runtime-expand-and-validate-004) lists what it adds. The contract stage (removing `projects.task_workflow` and the task workflow columns, enforcing required references) is a later migration owned by the schema owner after the replacement composition is live; the added columns are nullable here and the current composition keeps reading and writing the legacy ones.

**Appended contribution (T-185, durable run state):** [005_durable_run_state.sql](../../internal/storage/migrations/005_durable_run_state.sql) adds what the kernel's `runtime.RunRecord` needs that `004` lacks, so a `StateStore` adapter (T-182) round-trips the whole record with no second source of truth in Go. It is expand-only and appended after `004`, which is unchanged. [Durable run state](#durable-run-state-005) lists it. The contract stage is still later.

**Appended contribution (T-189, wait decisions and materializations):** [006_wait_decision_and_materializations.sql](../../internal/storage/migrations/006_wait_decision_and_materializations.sql) closes three gaps the PostgreSQL `StateStore` adapter (T-182) found: a wait decided before its step settles, a durable record of secret materializations, and a guard on recorded step outputs. It is expand-only and appended after `005`, which is unchanged. [Wait decisions and materializations](#wait-decisions-and-materializations-006) lists it.

| --- | --- |

| `users` | Global external principal mapping, unique `(issuer, subject)`; tenant-filtered visibility |
| `memberships` | Tenant/project role binding; tenant-wide bindings have null project; null-safe uniqueness |

(`005`) adds the attempt, the retained `when` evaluation, the workload result code and reason and the wait cancellation reason, and lets a wait record its identity before it opens. Resource commands belong to no step and live here, not on `run_steps`. |
| `run_workload_observations` | (`005`) The latest observation of each workload attempt, keyed by step and attempt: the binding (workload identity, specification digest, backend, fence), phase (`running`, `exited`, `absent`, `unknown`), result and observation time. |
| `run_materializations` | (`006`) The durable identity of one step attempt's secret material, keyed by tenant, project, run, step and attempt: the derived materialization identity, `issued` or `revoked` state, issue time, and the revocation time and optional evidence. | `run_resource_observations` | (`005`) The latest observation of each workspace or service of a run, keyed by kind, name and identity: owner, lifetime, handle fence, state, reason and observation time. A workspace is represented as well as a service. |
| `services` | Tenant/project/run scope, image/configuration, endpoint/runtime identity, status; scope and nullable owners are checked together |
| `secrets` | Tenant/project name, ciphertext, self-contained encryption envelope and key reference, version, revocation timestamp |
| `artifacts` | Immutable external metadata, producing run/optional step/task, URI, kind and digest. Preview URLs may have no content digest |
| `agent_sessions` | Project/run/step, optional task, model, status, usage counters, messages or transcript reference, result |

| `audit_events` | Immutable actor/resource/payload/time plus mutable publication timestamps, retry count and next attempt time |

JSON is for documents and snapshots. Ownership, identities, queryable states, versions and references remain relational. No independently editable `steps` definition table, raw-YAML mirror or separate trigger document duplicates `pipelines.definition`. YAML presentation is reconstructed from the stored document; comments/formatting remain in Git.

## Ownership and constraints

- Every tenant-owned relation has explicit `tenant_id`; project records also carry `project_id`. Composite foreign keys reject cross-project references even within one tenant.
- A repository's relative name may contain nested slash-separated segments; tenant-level repositories use `context`. Routing resolves existing tenant/project keys and authorizes creation before associating the repository. A path is not permission to create a project.
- Null-safe unique constraints cover tenant-level memberships, repositories, services, secrets and MCP registrations, and API-managed pipelines with no repository.
- `services.scope = pipeline` means **one run's lifetime**: both project and run are required. Project services have no run; tenant services have neither. Long-lived service reconciliation is Phase 3.
- Artifact/session step references include the producing run ID, preventing attribution to a step in a different run.
- MCP secret references carry the secret's project scope separately. A project may select its own or a tenant-shared secret, never another project's. Tenant-wide MCP registrations cannot select a project's private secret.
- Runtime cannot rewrite run inputs, source/binding/definition snapshots, artifact metadata or event payloads. State updates have narrow column grants. Runtime cannot truncate tables or access the migration ledger.

## Pipeline ownership and task projection

A project's process definitions are its pipelines. Pipeline names are unique within a project; the repository is the definition source, not a second naming scope. A task selects one pipeline and may have several runs through explicit reruns or rework. Run and step records own execution truth.

The target task fields are execution projections: selected pipeline, current run, status, current step, waiting assignment, result, and monotonic progress/version. Projection updates compare the run version so an older event cannot overwrite a newer run. The projection is rebuildable from `runs` and `run_steps`; it is not an independent workflow authority.

`projects.task_workflow` and the workflow-specific task fields are removed in the [pipeline-runtime simplification](pipeline-runtime-simplification.md). A wait is persisted with its run step and records a unique identity, expected input, accepted result, deadline, and consumed signal. Resolution records an authorized input against the exact run, step, and wait; the pipeline decides the next branch. A role inbox is a query over current waits, not a blocking task that drives a second state machine.

The task persistence port has memory and PostgreSQL adapters with one shared contract. Its transaction joins task, run-projection and audit/outbox appends. SQL locks the task before reading its current run; memory uses one `memdb.Update`. Authorization, trigger dispatch, reference-peer wiring and API operations belong to the shell.

## Pipeline-runtime expand and validate (`004`)

[004_pipeline_runtime_expand.sql](../../internal/storage/migrations/004_pipeline_runtime_expand.sql) is one transaction: the runner applies it atomically with its ledger row, so a refusal leaves no partial object, no data change and no ledger entry. It is stages 1 and 2 of [P2.1](pipeline-runtime-simplification.md#p21-schema-contribution); nothing is dropped. Two existing check constraints are replaced because their old form forbade the new shape: `run_steps_image_check` (an image is required) and `run_steps_status_check` (no `waiting` step state). Every legacy column named above stays readable and writable.

### Validation and mapping

Validation runs before any change and aborts the whole migration with a message that names the first conflict and says nothing was changed.

**Concurrent writers.** The first statement is `LOCK TABLE pipelines, runs, tasks IN SHARE ROW EXCLUSIVE MODE`, held through validation, mapping and commit. The runner's advisory lock serializes migration runners, not application transactions; without the table lock a run committed after the ambiguity check but before the mapping would be mapped without having been validated. The lock makes application inserts, updates and deletes on those tables wait until the migration ends (readers continue), so a concurrent admission either commits before the checks and is validated with them, or runs after the migration. An in-flight admission delays the migration until it ends; a migration that cannot start because writers never pause is retried by the operator.

- **Duplicate pipeline names** (SQLSTATE `23505`). The baseline key `(tenant_id, project_id, repo_id, name)` admits one name from an API definition and from several repositories. The migration refuses any `(tenant_id, project_id, name)` defined by more than one row. It never merges definitions, never picks a repository or a row, and never deletes. After the check passes it adds `pipelines_name_unique UNIQUE (tenant_id, project_id, name)`; the baseline key stays until the contract stage. The operator resolves the conflicting definition sources and reruns.
- **Ambiguous task-to-pipeline mapping** (SQLSTATE `23514`). The only existing evidence of a task's pipeline is its runs. A task whose runs name more than one pipeline cannot be mapped without choosing, so the migration refuses it. When every run of a task names the same pipeline the migration records that pipeline in `tasks.pipeline_id`; a task with no run stays unmapped and needs an explicit mapping before the contract stage requires the reference. A pipeline is never created or chosen, no run is made current and no projection field is set.

### Added columns

- **`runs`:** `lease_owner`, `lease_expires_at` (both null or both set), `lease_fence` (default 0; never decreases, and a new holder must take a higher fence, enforced by trigger `runs_guard`); `resource_identity`, `resource_spec_digest` (immutable once set); `cleanup_state` (`none`, `pending`, `retained`, `done`), `cleanup_attempts`, `cleanup_next_at`, `retained_resources` (a bounded JSON array that is non-empty when `retained` and empty when `done`). `cleanup_pending` stays. Unique key `(tenant_id, project_id, task_id, id)` is the target of `tasks.current_run_id`.
- **`run_steps`:** `step_kind` (default `container`; the image is required for a container and null for a wait, and a wait holds no runtime identity, exit code, log, workload or command intent); `workload_id` and `workload_spec_digest` (immutable once set); `command_intent` (`launch`, `stop`, `remove`) with its lease fence and time, committed before the external effect and requiring a workload identity; `launch_evidence` (`none`, `not_started`, `started`, `uncertain`); `workspace_held`, true only for a running container step and unique per run, so one executable step holds the workspace at a time.
- **Wait columns on `run_steps`** (all null for a container step and, as `004` created them, for a wait that has not opened; [`005`](#durable-run-state-005) lets an unopened wait carry its identity, version and assignment and a wait cancelled before opening carry none of the opened content): `wait_id` (unique per project), `wait_assignment`, `wait_correlation` (an object of up to four keys), `wait_request` (at most 4 KiB), `wait_input`, `wait_outcomes` (1–8 names, never `expired` or `cancelled`), `wait_approving` (one declared outcome), `wait_on_expiry` (`fail` or `continue`), `wait_deadline_at`, `wait_state` (`waiting`, `resolved`, `expired`, `cancelled`), the result (`wait_outcome`, `wait_answer`, `wait_actor_ref`, `wait_decided_at`), `wait_consumed_signal_id` and `wait_version`. The step status `waiting` is valid only for a wait step in state `waiting`. A resolved wait has a declared outcome, an actor and a consumed signal; an expired `continue` wait has the reserved outcome `expired` and an expired `fail` wait none; [`006`](#wait-decisions-and-materializations-006) lists the step statuses each decision may sit on (a decided wait may sit on a step that is still `waiting`, otherwise `succeeded` for a resolved or `continue` wait and `failed` for a `fail` wait); a cancelled wait has no outcome, actor or signal. Trigger `run_steps_guard` makes identity, correlation, expected input and deadline immutable once opened, permits only `waiting` to `resolved`, `expired` or `cancelled`, makes a decided wait immutable including its `wait_version`, requires every change to an opened wait to raise `wait_version`, and rejects any decrease or clearing of an initialized `wait_version` even when it is the only column written. The store's clock comparison between a resolution and the deadline stays in the version-checked decision of the use case.
- **`tasks`** (all nullable; the existing `assigned_role` is the projected assignment role): `pipeline_id` (same project; immutable once set), `current_run_id`, `status` (`pending`, `queued`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`), `current_step_key`, `waiting_for`, `result` (at most 16 KiB), `progress_version`, `progress_run_version` (both set or both null). A task with no current run projects nothing beyond `pending`; one with a current run has a pipeline and a status. Trigger `tasks_guard` compares versions with explicit NULL handling: an initialized `progress_version` or `progress_run_version` can neither be cleared (clearing both would otherwise satisfy the pair constraint and let lower versions be restored) nor decrease, except that the run version may restart when `current_run_id` changes to a different run. An older run's event cannot overwrite a newer view.
- **Composite ownership:** `tasks_current_run_fk (tenant_id, project_id, id, current_run_id) REFERENCES runs (tenant_id, project_id, task_id, id)` proves the current run belongs to that task and project, not merely the project; it is unchecked while `current_run_id` is null. `tasks_pipeline_fk` keeps the selected pipeline in the task's project.

### Signal records

`signal_records` holds one row per recorded signal identity `(tenant_id, project_id, caller_principal, caller_key)` (primary key), the opaque `signal_id` the shell derives (unique per project; the only form that appears in events and in `run_steps.wait_consumed_signal_id`), the request digest, `applied` (true only for the winner) and `refusal_reason`. It has two shapes, selected by `shape`:

| Shape | Retains | Constraints |
| --- | --- | --- |
| `decision` | The original target (`target_run_id`, `target_step_id`, `target_wait_id`) and the complete replayable decision: `decision_kind` (`resolved`, `expired`, `cancelled`), `decision_outcome`, `decision_answer`, `decision_actor_ref`, `decision_version`, `decided_at`. A refusal that lost to a decision (`decided`) records that decision; `version_conflict` and `invalid_outcome` record only the reason. | A winner is a complete `resolved` decision; a wait has at most one winner (partial unique index); a refusal is never applied |
| `tombstone` | Identity, request digest, refusal reason (`unknown_wait` or `ambiguous_correlation`) and `recorded_at`; no target or decision | Any target or decision column is refused |

A record carries no foreign key to a run, step or wait, so ordinary retention that removes them never removes the decision needed to replay a signal. The only reference is the project, `ON DELETE CASCADE`: a record is removed only with its project, and it has no expiry column. The runtime role has `SELECT` and `INSERT` only, so a recorded result is never modified. `run_steps.wait_consumed_signal_id` references the record by a deferred foreign key, so the winning record and the decision commit in one transaction in either order, and a decision without its record fails at commit.

### RLS and grants

`signal_records` enables and forces RLS with the owner policy and the tenant predicate used by every table. The runtime role may update only lifecycle columns: run lease, resource identity and cleanup columns; step workload, intent, workspace and wait columns; task `pipeline_id` and projection fields. Admitted inputs, snapshots, ownership keys, `step_kind`, `image` and `step_key` remain outside its column grants, and the guard triggers apply to every writer including the owner. Real-PostgreSQL migration tests cover the new constraints, forced RLS under a non-owner role, append-only records, rollback and the refusal paths.

## Durable run state (`005`)

[005_durable_run_state.sql](../../internal/storage/migrations/005_durable_run_state.sql) is one transaction like `004`: a failure anywhere leaves no object, no backfill and no ledger row. Nothing is dropped; `projects.task_workflow` and the legacy task columns are not touched. Four check constraints (`run_steps_container_no_wait`, `run_steps_wait_unopened`, `run_steps_wait_open`, `run_steps_wait_cancelled`) and the function `kodama_run_step_guard()` of `004` are replaced because their old form forbade a wait that has an identity but has not opened. The plan of a run is `runs.definition_snapshot`; the unit test `Test_unit_storage_durable_run_state` fails when a field of `runtime.RunRecord` has no column.

| Record | Stored in |
| --- | --- |
| `Run` | `runs`: `status` (the outcome), `reason`, `cancel_requested_at`, `version`; `cleanup_state` (`none`, `pending`, `retained`, `done` are the kernel's `not_started`, `pending`, `exhausted`, `complete`), `cleanup_attempts`, `cleanup_max_attempts`, `cleanup_reason`, `retained_resources` |
| `Claim` | `runs`: `lease_owner`, `lease_purpose`, `lease_fence`, `lease_expires_at` |
| `Step` | `run_steps`: `status`, `reason`, `version`, `attempt`, `result_code`, `exit_code`, `result_reason`, `when_*` |
| `Wait` | `run_steps`: `wait_*` |
| `Command`, `WorkloadObservation`, `ResourceObservation` | `run_commands`, `run_workload_observations`, `run_resource_observations` |

**`runs`.** `lease_purpose` (`execute`, `reconcile`, `cleanup`) is non-null exactly when `lease_owner` is. `cleanup_max_attempts` (at least 1, default 1) is the retry bound fixed at admission; the runtime role cannot update it, and `cleanup_attempts` never exceeds it. `cleanup_reason` is a stable code kept only while cleanup is `pending` or `retained`, and a `retained` run always has one. `retained_resources` holds both the retained resources and the retained workloads, one tagged entry each (`{"resource": ...}` or `{"workload": ...}`), bounded at 256 entries. Existing rows are mapped by four narrow statements that touch only rows that would otherwise violate the new constraints (a held lease becomes an `execute` claim, a cleanup bound is raised to the attempts already recorded, a `retained` run gets `cleanup_exhausted`, a cancelled wait gets the reason its step state implies); on a database written only by the `004` schema none matches.

**`run_commands`** (primary key `(tenant_id, project_id, run_id, command_id)`). `step_key` references the step in the same run and is null for a resource command. A workload command names its step and carries `spec_digest`, `binding_attempt` and `binding_backend`; a resource command carries no binding. The workload binding's scope, run, step, workload identity, specification digest and fence are this row's `tenant_id`, `project_id`, `run_id`, `step_key`, `target`, `spec_digest` and `fence` (the kernel requires them equal), so only the attempt and the backend are separate columns. `intent` and `confirmed` have no reason; `rejected` and `uncertain` require one. Only a confirmed workload command records a result (`result_code`, `result_exit_code`, `result_reason`), and a success has exit code 0 and no reason. Trigger `run_commands_guard` keeps identity, target, specification, fence, binding and record time fixed, allows `intent` to settle into any outcome and `uncertain` into `confirmed` or `rejected`, makes `confirmed` and `rejected` final, allows a reason to change only with a settlement, and keeps a recorded result once written. The runtime role has `SELECT`, `INSERT` and `UPDATE (state, reason, result_code, result_exit_code, result_reason)`.

**`run_workload_observations`** (primary key `(tenant_id, project_id, run_id, step_key, attempt)`, step reference in the same run). The binding is `workload_id`, `spec_digest`, `backend` and `fence`. Only an `exited` workload has a result. Trigger `run_workload_observations_guard` keeps the attempt, workload identity, backend and specification digest fixed, never lets the fence or the observation time decrease, and lets an `exited` observation only be repeated with the same result or confirmed `absent`. The runtime role may update `fence`, `phase`, the result columns and `observed_at`.

**`run_resource_observations`** (primary key `(tenant_id, project_id, run_id, kind, name, identity)`). `kind` is `workspace` or `service` and a workspace is always pipeline-lifetime. The handle's scope is the row's tenant and project; its owner is the tenant alone for `lifetime = tenant` (`owner_project_id` null) and the row's own project otherwise, never another project; `handle_run_id` is the observing run for a pipeline-lifetime resource and null or that run otherwise. Trigger `run_resource_observations_guard` keeps the resource, owner, lifetime and run fixed and never lets the fence or the observation time decrease. The runtime role may update `fence`, `state`, `reason` and `observed_at`.

**Step evidence.** `attempt` (default 0) belongs to container steps, is 0 while pending, and never decreases. `when_evaluated` (default false) with `when_result`, `when_input_digest` (1–128 characters) and `when_evaluated_at` record the retained predicate: an unevaluated predicate has none of the others, which differs from an evaluated `false`; a false evaluation ends in `skipped` with `condition_false`, `cancelled` or the step is still pending. The evaluation is written once: the guard refuses any later change, flip or clearing. `result_code` (`succeeded`, `failed`, `cancelled`, `timed_out`, `lost`) with `result_reason` is the container step's settled workload result and agrees with its status; the exit code is the existing `exit_code`; a wait never has one. A settled step keeps its attempt, exit code and result. All of these are in the runtime update grant, together with `wait_reason`.

**Pre-open waits (the choice).** The wait columns stay on the step row and the constraints are relaxed in two exact ways, instead of adding a waits table: the pending wait is the same record as the open one, the guard already makes it version-checked, and a second table would duplicate the step's lifecycle and the unique wait identity. (1) A wait step that has not opened (`wait_state` null) may carry `wait_id`, `wait_version` and `wait_assignment`, which are recorded at admission; `wait_id` and `wait_version` are both set or both null, the assignment needs an identity, and nothing else is set. (2) An opened wait is unchanged: `waiting`, `resolved` and `expired` still require the correlation object, `wait_input`, `wait_outcomes`, `wait_on_expiry` and `wait_deadline_at` together with the identity and version, and an assignment or a non-empty correlation. The single exception is `cancelled` with none of the opened content (no correlation, request, expected input, outcomes, approving outcome, expiry or deadline), which records a wait cancelled before it ever opened. `wait_reason` (`run_cancelled` or `run_failed`) is required exactly for a cancelled wait. The replacement `kodama_run_step_guard()` keeps `004`'s rules and fixes three things: the wait identity is immutable from the moment it is recorded, every change to a recorded wait (including reassignment before it opens, opening it, or cancelling it before it opened) must raise `wait_version`, and a move out of the unopened state is only to `waiting`, or to `cancelled` with no deadline; the state test uses `coalesce` so an unopened (null) state cannot slip through an unknown comparison. A decided wait stays immutable, including `wait_reason`.

**RLS and grants.** The three tables enable and force RLS with the owner policy and the tenant predicate of every table, and reference the run (and step) by the composite tenant/project key. The runtime role has `SELECT` and `INSERT` on each and the column updates named above, and no `DELETE` or `TRUNCATE`; identity, target, specification and binding columns are insert-only. On `runs` it additionally updates `lease_purpose` and `cleanup_reason`; on `run_steps` the attempt, `when_*`, `result_code`, `result_reason` and `wait_reason`. Real-PostgreSQL tests (`Test_durable_run_state_postgres`) run as a non-owner role: a mid-flight and a settled `RunRecord` (lease, retried launch, resolved wait, pending wait, wait cancelled before opening, false and true `when` evaluations, uncertain command, workspace and tenant-owned service observations, exhausted cleanup with retained resource and workload) round-trip exactly; each guard rejects its regression; tenant A and tenant B cannot read or write each other's rows; a failed transition, including one refused at commit, leaves no partial row; and a failure inside `005` rolls it back whole while a `004` database upgrades.

## Wait decisions and materializations (`006`)

[006_wait_decision_and_materializations.sql](../../internal/storage/migrations/006_wait_decision_and_materializations.sql) is one transaction like `004` and `005`: a failure anywhere leaves no object and no ledger row. Nothing is dropped, no row is rewritten, and the legacy task columns are not touched. Three check constraints of `004` (`run_steps_wait_resolved`, `run_steps_wait_expired`) and `005` (`run_steps_wait_cancelled`) are replaced because their old form forbade a decision on a step that had not settled; the other constraints and the guard function `kodama_run_step_guard()` stay as they are.

**Wait decisions before settlement.** The kernel decides a wait independently of its step: a signal resolves or expires an open wait and leaves the step `waiting` for the engine to settle, and a run's cancellation cancels a pending or open wait and leaves its step for the engine. The replacements keep every requirement on the decision itself and widen only the step status:

| Decision | Step status allowed |
| --- | --- |
| `resolved` (declared outcome, actor, time and consumed signal) | `waiting` (decided, not yet settled) or `succeeded` |
| `expired` with `on_expiry: continue` (reserved outcome `expired`) | `waiting` or `succeeded` |
| `expired` with `on_expiry: fail` (no outcome) | `waiting` or `failed` |
| `cancelled` (reason `run_cancelled` or `run_failed`, no outcome, actor or signal) | `pending` (the wait never opened), `waiting`, or `cancelled`, `failed` or `skipped` |

Everything else is as before. `Test_unit_storage_wait_decision_ordering` compares each replacement with the constraint it replaces after masking the status test, so a decision cannot lose a required column unnoticed, and cross-checks the allowed pairs with the kernel's `CheckStepWait`. An opened wait still needs `run_steps_wait_open`; an unopened wait still has no decision and no `waiting` status (`run_steps_wait_unopened`); `run_steps_wait_waiting` still requires an open wait to be `waiting` and carry no decision. The decision is stored once and is immutable by `005`'s guard, which also refuses to move a decided wait back to `waiting`, to change its version, or to decide it a second time. One new trigger closes the one hole the relaxation opens: `run_steps_wait_order_guard` (function `kodama_run_step_wait_order_guard()`) makes the status of a wait step move only forward, so a step that still shows `waiting` beside a decided wait can settle, but a settled wait step never changes state and a `waiting` one never returns to `pending`; a decided wait therefore never appears to reopen through its step. One pairing remains looser in the kernel than in the table: `CheckStepWait` accepts a `failed` step beside an expired `continue` wait; the table has never stored it and still does not.

**Step outputs.** `run_steps.outputs` existed without a guard, so the rule that a settled step's outputs never change lived in Go alone. Trigger `run_steps_outputs_guard` (function `kodama_run_step_outputs_guard()`) accepts a change to `outputs` only in the update that moves a step from an unsettled state to `succeeded`, and refuses any other change: outputs on a running, failed, skipped or cancelled step, and any rewrite, extension or clearing after settlement, for every writer including the owner. An update that leaves the value as it is (a replay of the settling commit) is not a change. The runtime role's grant on `outputs` is unchanged.

**`run_materializations`** (primary key `(tenant_id, project_id, run_id, step_key, attempt)`; references the run and the step within the run, without cascade). `materialization_id` is the identity the kernel derives from the key (`mat:<tenant>:<project>:<run>:<step>:<attempt>`, `runtime.NewMaterializationRef`) and a check requires exactly that, so a record cannot name material it was not issued for. `state` is `issued` or `revoked`; `issued_at` is the kernel's time and has no default; `revoked_at` is set exactly when the record is `revoked` and not before `issued_at`; `revocation_evidence` is an optional reference of 1–256 characters to the resolver's confirmation, allowed only on a revoked record. The record carries no directory and no value. Trigger `run_materializations_guard` makes the key, identity and `issued_at` immutable and makes `revoked` final: neither the state, the time nor the evidence changes once revoked, while a repeat of the recorded revocation is not a change, as the kernel's `CheckMaterializations` repeats are not. The partial index `run_materializations_unrevoked` serves the scan for material that still needs revoking. RLS is enabled and forced with the owner policy and the tenant predicate. The runtime role has `SELECT`, `INSERT` and `UPDATE (state, revoked_at, revocation_evidence)`; identity and issue time are insert-only and nothing is deletable.

**Evidence.** `Test_unit_storage_wait_decision_ordering` and `Test_unit_storage_materialization_records` check the migration text and its fit with the kernel without a database. The real-PostgreSQL tests `Test_wait_decision_ordering_postgres`, `Test_step_outputs_immutable_postgres` and `Test_materialization_records_postgres` run as a non-owner runtime role (no ownership, no `BYPASSRLS`): a decided wait persists while its step stays `waiting` and never reopens; a materialization records issue and revocation once with `revoked` final, taking each transition the kernel takes and refusing each it refuses; outputs cannot be rewritten after settlement; tenant B cannot read, write or change tenant A's records; and a refused write, including a transaction whose later statement fails, leaves no partial row.

## Transaction boundaries

- Task mutation: task lock, expected task/progress version, current-run projection change and event append commit together. No network call runs in that transaction.
- Admission: persist the entire run snapshot and its step records together. `runs.trigger_key` identifies one logical trigger delivery per pipeline. User submission deduplicates `(project, principal, request_key)`; `request_hash` is compared, not part of the unique key.
- Outbox: commit the event with state, publish outside SQL using its stable ID, then update publication progress. A crash may redeliver. Consumers use resource uniqueness or transactional version checks; JetStream alone does not make database effects exactly once.
- Git and container effects remain outside SQL transactions. Durable reconciliation of external effects is a Phase 3 responsibility, not removed by the smaller schema.

## Secrets and run history

The single secret row contains ciphertext and envelope metadata sufficient to decrypt it with its referenced KMS/keyfile wrapper. Authenticated data continues to bind ownership, secret ID and revision. Ordinary configuration lives in the project or pipeline document.

Runs retain secret identity/revision references, not plaintext. If a current-only secret has rotated or been revoked before use, resolution fails rather than silently substituting its new value. A new run can bind the new revision. Historical secret-value recovery is not supplied by this schema.

## RLS and migration policy

All product tables, including `git_credentials`, enable and force RLS. `WithTenant` sets validated transaction-local context under a non-owner role. Global user visibility is filtered through memberships; principal discovery and worker tenant enumeration use narrow, PUBLIC-revoked definer functions. Tenant RLS is supplemented by project predicates and operation authorization.

This is an intentional **fresh-database prerelease reset**. A database that already holds the three-migration baseline is upgraded only by appending `004`, `005` and then `006`; `004` validates its data first and changes nothing on refusal, and neither rewrites an applied checksum. Existing checksums are rejected before applying changes; the migration runner never drops or rewrites an existing database. Use a new isolated database for the reset. Later migrations append to this new baseline. The storage contribution contains the two baseline migrations, the Git hosting contribution `003_git_hosting.sql`, the pipeline-runtime expand contribution `004_pipeline_runtime_expand.sql` the durable run-state contribution `005_durable_run_state.sql` and the wait-decision contribution `006_wait_decision_and_materializations.sql`, in that order; legacy run-resource/grant/provenance contributions are not appended.

No deployed database was reset as part of Phase 2. The legacy server explicitly refuses the new schema until Phase 3 replaces its adapters.
