# M3 full SDLC acceptance (T-044)

This is the reproducible report of the M3 checkpoint. It drives the actual core assembly (`internal/app`, `KODAMA_ENV=test`) through its public API over the services of the `test` environment ([ADR 0009](../adr/0009-environments.md)): real PostgreSQL (runtime role, forced row-level security), JetStream, S3, a Git host over TLS, an OCI registry, the Podman runtime and a kind namespace as the stage's deployment target, with the business-loop installation statement of T-075 selected exactly as an installation selects it: the ChatOps destination policy and canonical review-link origin, and the QA mapping principal. The deployment tools, the step entrypoint, the delivery scripts, the gates, the outbox/inbox event path, the notification worker and its outbound client, the dependency graph and the flow summaries are the production ones. What is deterministic and test-owned is listed under [Fixture notes](#fixture-notes). Nothing here is a browser, live-provider, wrapper-image, Kubernetes-runtime, hosted or production qualification (T-069, T-085, T-089, T-090).

**Status: the nine acceptance checks pass against the real stack, and the journey stops where the composition does.** `m3_business_loop`, `m3_rejection`, `m3_notification_outage`, `m3_dependencies`, `m3_metrics`, `business_loop_assembly`, `business_loop_gate_links`, `business_loop_event_replay` and `chatops_gate_integration` pass. The assembled core cannot move a work item into review, so **the explicit human completion (`review → done`), the rework and reopen entries into active, and the review/reopen intervals could not be demonstrated** ([finding 1](#findings)). That is a missing production join, recorded as an executable fact (`TestM3ReviewGuardNotWired`), not hidden behind a passing check; it needs a prerequisite task before M3 can be called accepted. Read [Findings](#findings) and [Open items and deviations](#open-items-and-deviations) before relying on this report.

## Running it

```sh
DEV_STACK=cluster make check-go-integration \
  PKGS="./test/e2e/m3/... ./test/integration/assembly-business-loop/..."
```

The default stack is `cluster`: the stage's deployment target is the scope's kind cluster (`KODAMA_TEST_KUBECONFIG`), which the tests that stage obtain through `m2kit.RequireCluster` (it **fails**, never skips, without one; on a `services` scope the M2 kit creates a shared kind cluster exactly as [the M2 report](m2.md#running-it) describes). The tests that need no cluster (`m3_dependencies`, `m3_metrics`, `m3_notification_outage` and the four assembly checks) run on the same scope. `check-go-integration` provisions a missing scope, preflights it and loads `host-env.json`; the suites fail when Podman, Git, `git-http-backend`, `curl`, `openssl`, `kubectl` or the registry is missing. The two packages run concurrently; the suites take about two to four minutes each on a quiet machine (the journey scenarios are twenty to thirty seconds apiece once the tools image is built).

### Fixture notes

* **The M3 kit** (`test/e2e/m3/kit`) **wraps the M2 kit** (`test/e2e/m2/kit`, imported, not forked): the same stack, world, Podman, registry and cluster fixtures, plus the business-loop statement. Both new packages call the M2 kit's `Main` and reuse its tools image once per test process.
* **The notification receiver** is a local TLS server (`internal/integrations/chatops/chatopstest`) the installation allows as an exact tenant-scoped private endpoint (the policy has no CIDR or allow-all form); its behavior (accept with a receipt, 503, lose the response, hang) is the test's. **The canonical link origin** is a TLS front of the public API, so a link in a payload is a real `https` URL a person (the test, with a token) can follow.
* **Identities.** The human reviewer is the `reviewer` persona (and `analyst`, bound as a second reviewer); the QA mapping principal is its own user (`qa-mapper`, bound as analyst, the role with read/create/edit-spec work permission), distinct from the reviewer and from every workload. A user exists only after its first login, so the kit binds it and restarts the process with its identifier in the statement. The administrator configures destinations (`project:settings`), the engineer starts work.
* **The candidate** is written by a human (the engineer pushes it to the work branch of the real Git host): the M2 quality/build/manifest files plus `ci/e2e.sh`, the candidate's own end-to-end check. Agent-produced candidates, conformance evidence and the build-after-gate flow are M2's (T-038); the M3 journey starts from a candidate with a verified image. The deterministic build republishes the shipped tools image into the project's repository of the scope registry (as in M2), so every candidate's image **digest is the same**; the candidate commit, the deployment, the configuration digest and the gate subject are what differ between a first candidate and its rework.
* **The deterministic exploratory QA** (`test/e2e/m3/kit/qa.go`) is a `/bin/sh` program run as a container step in the tools image. It declares the stage environment (so the admission pins its configuration), reads the deployment it inspects from its pinned inputs, registers a browser trace as a declared file output through the runtime API with its own token, and returns the structured report (`internal/qa/schema.json`) as its declared output. `QA_MODE` selects a clean pass or one finding. It stands where the T-069 browser profile will, not as a browser.
* **The control plane's mapping call.** The business-loop slice has no route or trigger for the QA mapping (the scan that calls it is T-069), so the tests call `Core().BusinessLoop.QA.Record` as the trusted control-plane caller after the attempt's accepted result, the call that trigger will make. The service refuses a user, a workload and an operator as callers.
* **Fault injection and expiry.** The M2 front's fault hook (`Front.Faults`) drops the response of the stage's deployment registration and outcome after commit. The expiry case uses a preview environment (TTL 75 s; the API minimum is 60 s) with the project's cleanup pipeline in an installation of its own (the cleanup pipeline names one environment) and a second replica; the sweep interval is the M2 kit's two seconds. The lost-request and lost-cleanup-acknowledgment cases stay in `delivery_assembly_replay` (M2).
* **Flow summaries** are read through `Core().BusinessLoop.Flow` (the slice's service over the runtime role's database): the summary contribution to the work list needs a hook in the work-list handler that no task owns yet and is recorded as not wired by the slice (`flow-summary-list`).
* No SQL edits fabricate a state; SQL is used to read (and to count rows under the runtime role's forced row-level security).

## Findings

1. **The assembled core cannot move a work item into review, so human completion is unreachable.** `internal/app/core.go` builds the work store's guards with the dependency guard (T-075) and the writer guard and leaves `work.TxGuards.Subjects` unset ("no transaction-safe adapter exists yet"); the guard that verifies a candidate's history and evidence needs Git and object reads outside the transaction. No production `SubjectGuard` exists (the only ones are the test doubles and the QA module's narrowing guard that refuses commits). Every `active → review` therefore fails closed (`TestM3ReviewGuardNotWired`), and with no recorded review subject nothing can reach `done`, be reworked (`review → active`) or be reopened (`done → active`). Consequences for this report: `m3_business_loop` and `m3_rejection` prove the accepted and rejected *gate* paths, the linked defect and the fresh review, and prove only the **negative** half of WM-A05 and DQ-A09 (a passing run, an approved gate, the QA principal and non-reviewers cannot complete); the **positive** half (a current authorized human completing with the observed content revision and candidate, naming acknowledged findings), the WIP guard of rework and reopen (WM-A03's second half) and the review and reopen intervals of WM-A08 are not demonstrated here. `internal/app` and the work module's postgres adapters are outside T-044's paths; a prerequisite task owning a transaction-safe review-subject adapter is needed, after which these steps join the journey tests: item to review with the staged candidate and the gate's evidence, a wrong-revision and a stale-candidate completion refused, the explicit `review → done` by the reviewer, a rejected review's `review → active` contending for the WIP slot, a reopen, and the review and reopen intervals in `m3_metrics`.
2. **A container step cannot cite its own screenshots.** The entrypoint uploads declared file outputs only after the command ends and types them by extension (`.png` is `application/octet-stream`), while the QA mapping requires a screenshot to be an image and every cited artifact to be named by the accepted result. The deterministic QA therefore pre-registers a declared output (an identical repeat of a reservation is a replay) and cites a *trace*; screenshot evidence belongs to the browser profile's wrapper (T-069). The mapping's behavior for screenshots is qualified by its own module tests (T-040).
3. **The M2 kit's image cleanup is not safe between concurrent packages.** `kit.Main` builds the tools image and pushes it to the scope registry under names that do not depend on the process, and removes them by name when the process ends. Two packages running together (as this check's two do) therefore race: the package that finishes first removed an image the other still ran, and the rework stage of `TestM3Rejection` failed `startup_timeout` after four minutes (reproduced three times). The assembly package of this task needs neither the tools image nor a cluster, so its `TestMain` sets a `-run` filter that matches every test (the kit then builds on demand, never) and the e2e package is the only one that builds. The kit (T-038's, not owned here) should give its image names a per-process component; until then a package that does not need the image must not trigger the warm-up.
4. **Notifications do not depend on the broker.** The event module's repair reads the committed outbox itself, so a notification is made exactly once while the broker is unreachable; the later publication is a no-op for the consumer. `TestBusinessLoopEventReplay` pins this (and the exactly-once property it relies on).
