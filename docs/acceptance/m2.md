# M2 agent-to-preview acceptance (T-038)

This is the reproducible report of the M2 checkpoint. It drives the actual core assembly (`internal/app`, `KODAMA_ENV=test`) through its public API over the services of the `test` environment ([ADR 0009](../adr/0009-environments.md)): real PostgreSQL (runtime role, forced row-level security), JetStream, S3, a Git host over TLS, an OCI registry, the Podman runtime, and a kind namespace as the preview's deployment target and nothing else. The model gateway, the MCP proxy, the qualified wrapper tuples, the runtime action ceiling, the registry verifier, the delivery tools and the native Git trigger are selected exactly as an installation selects them (T-101's operator statements). Model, tool and agent behavior is deterministic and test-owned; nothing here is a live-provider, wrapper-image, Kubernetes-runtime or production qualification (those stay T-085, T-089 and T-090).

**Status: all nine acceptance checks pass against the real stack**: `m2_agent_preview`, `m2_rework`, `m2_needs_input`, `m2_stale_review`, `m2_tool_budget`, `agent_delivery_assembly`, `gate_consumption_atomicity`, `delivery_assembly_replay` and `native_hook_roundtrip`. The production joins round 1 reported missing (T-096..T-101) are on `main`; the executable "fails closed where joins are missing" cases they replaced are gone. What is still open is listed under [Open items and deviations](#open-items-and-deviations); read it before relying on this report.

## Running it

```sh
DEV_SCOPE=batch DEV_STACK=cluster make check-go-integration \
  PKGS="./test/e2e/m2/... ./test/integration/assembly-agent-delivery/..."
```

**The suite needs a kind cluster, which the `cluster` stack provides.** The preview's deployment target is the scope's kind cluster (`KODAMA_TEST_KUBECONFIG`, set only by that stack); the tests that need it call `kit.RequireCluster`, which **fails** (never skips) when no cluster can be had, and the tests that do not need it still run on the same scope. On a scope created as `services` (a stack cannot be changed without tearing the scope down, which a test must never do) the kit creates one kind cluster for the scope's test processes, shared by file lock and deleted by the last of them, with its node attached to the scope's registry network exactly as the cluster stack wires it; this fallback needs the `kind` binary a cluster scope installs. The suite is registered in `openforge.json` `mainCheck` on the existing `batch` scope (`DEV_STACK=cluster`), beside `make lint-go`, `make test-go-unit` and the M1 suites. `check-go-integration` provisions a missing scope, preflights it and loads `host-env.json`; the tests fail when the scope, Podman, Git, `git-http-backend`, `curl`, `openssl`, `kubectl` or the registry is missing. The three packages (`test/e2e/m2`, `test/integration/assembly-agent-delivery` and its `replay` package, split so that each stays inside Go's ten-minute default test timeout) run concurrently; wall time on a heavily loaded shared recording machine (load average above 20) was 7.0 minutes for `test/e2e/m2`, 6.1 for `replay` and 4.8 for the rest, and about 4 to 5 minutes each on a quiet one.

**Kernel key quota.** Every container holds a session key of the user's quota (`kernel.keys.maxkeys`, 200), which other scopes and tasks of a shared host can exhaust: containers then fail to start (`create keyring ... Disk quota exceeded`), inside the kind node too. The kit therefore creates its Podman containers with `keyring = false` (`KODAMA_TEST_PODMAN_KEYRING=1` keeps the default) and has the kind node's containerd set `NoNewKeyring`.

The deployment-tools image is built once per test process with its shipped `images/deployment-tools/build.sh` (set `KODAMA_TOOLS_IMAGE` to a prebuilt local image to skip the build), pushed to the scope registry and pulled by digest. The runtime's startup budget is raised from one minute to four in the kit: a shared host that starts many containers at once measures the host, not the product.

### Fixture notes

* **The kit is a fork of T-026's** (`test/e2e/m2/kit`, `base_*.go` plus the M2 additions), not an extension. M1's kit needs the `services` stack's workload network and an S3 forward; the `cluster` stack has neither. The M2 kit runs its Podman containers with `--network host`, reaches the services on their published `127.0.0.1` ports (LocalStack's S3 endpoint directly, no forward proxy), and fronts the runtime API with its own TLS listener. M1's kit is untouched.
* **The deterministic agent** is a `/bin/sh` program carried in the profile's *instructions*; a small catalogue bootstrap command (a catalogue command item is at most 512 bytes) joins the pinned payload's chunks, decodes the canonical payload to `/tmp/payload.json` and runs the instructions. There are two forms: BusyBox `wget` in the pinned Alpine image (`kit/agent.go`, behavior chosen by run inputs: outcome, model and tool call counts, a hold, a probe) and `curl`/`jq` in the tools image (`kit/erp.go`, the ERP agent). Both call the gateway and MCP proxy with their own runtime token. The ERP agent also writes the candidate (`CandidateFiles`: quality script, build script, manifests) into its checked-out `/workspace`, commits it, reserves and uploads a diagnostic artifact as design evidence through the runtime API, and declares the `conformance` artifact. It is not OpenCode and proves nothing about a real harness.
* **The ERP example runs as two runs** (see item 2 below): a candidate run (implement, test, review gate, build) and a promotion run (`preview`) whose inputs are the build's verified image artifact id, its reference and the candidate commit.
* **The deterministic "build"** republishes the shipped tools image's manifest into the project's own repository of the scope registry (cross-repository blob mount, then the manifest by digest) and reports it as the step's `ociArtifact` output. No image build runs in a restricted step container here. The core's real OCI verifier then fetches and registers it by digest.
* The profile's wrapper version equals the entrypoint's version (runtime admission compares them). The tools image is a second catalogue tuple (an installation statement) so it can be an agent's harness image.
* **Reaching the test process from containers.** The kit's containers share the engine's network (`--network host`). Where the engine runs on this host the test process is `127.0.0.1`; with a Podman machine it is `KODAMA_TEST_SERVER_CALLBACK_HOST` (`host.containers.internal`), which `kit.CallbackHost` returns. The runtime front, the workload front and the Git server are all built on that name. The Git server listens on every interface with a certificate covering that name and loopback, and its URL carries the name, so one URL serves the container's checkout and the server's own Git. The host cannot resolve the name, so `kit.Main` puts a `git` shim first on `PATH` that adds `http.curloptResolve` entries (the servers append `host:port:127.0.0.1` to `KODAMA_TEST_GIT_RESOLVE_FILE`); a rewritten URL would no longer match the credential's origin. The workload front forwards the upstream `Host` header, because the MCP handler's localhost protection refuses a foreign one. With the default `127.0.0.1` none of this is active.
* A second plain-HTTP front lets a container reach the gateway and MCP proxy; the runtime API keeps the TLS front. That front can inject faults (`Front.Faults`): lose a request before the server sees it, or lose the *response* after the server committed (the stream is aborted, as h2 cannot hijack).
* Gate scenarios that need the window between a decision and its consumption restart the process with the scan interval at an hour and the broker's proxy stopped (`HoldProgress`), change the world through the public API and let a normal-paced process recover from durable state (`ResumeProgress`). No SQL edits fabricate a state; SQL is used only to read.
* The hook scenario installs the shipped `post-receive` hook as the real bare repository's hook and mounts the trigger through the core's own service (`Core().Triggers.Service.Install`).
* The deployment scenarios create a restricted-Pod-Security namespace per scenario with a namespace-scoped ServiceAccount credential held as the project's kubeconfig secret; the test process alone holds cluster-admin.

## Open items and deviations

These are the places the suite stands somewhere other than the production ideal. None is hidden behind a passing check; each is either a deviation in the fixture or work another task owns.

| # | Item | Effect on the claims |
| --- | --- | --- |
| 1 | **The production joins of round 1 are resolved** (T-096 action ceiling, T-097 delivery reader/gate binder/runtime secret route, T-098 Podman source checkout, T-099 artifact output naming, T-100 and T-101 trigger adapters and bindings). The earlier findings 1 to 7 are closed and their fail-closed cases removed. | The nine acceptance checks run on the real production composition. |
| 2 | **The example cannot be one pipeline.** The validator refuses an `ociArtifact` reference in `env` or `args` (`TestM2ExampleEnvArtifactReference`), so the preview deploys in a second, promotion-form run fed by the candidate run's outputs. | `m2_agent_preview` is the example's behavior in two linked runs. Whether the example document or the validator should change is a documentation/contract decision outside T-038. |
| 3 | **Podman cannot run the shipped non-root tools image.** The runtime mounts bootstrap files as host-owned `0600` and runs the image's own user, so a uid 65532 image fails reading its CA bundle (`TestM2ShippedToolsImageOnPodman`). The suite runs a **root derivative** of the shipped image: `USER 0:0` and a per-process label, nothing else (`kit/image.go`). Rootless Podman root is the host user, every capability dropped, read-only root filesystem. | Every delivery claim is about the shipped scripts and packages running as root in a rootless container, not as uid 65532. A Podman-runtime fix (readable bootstrap files for the image's user) is a product task. |
| 4 | **Wrapper evidence binding is open (T-031/T-085).** The real wrapper records a claimed-passed check as `not_run` because it cannot bind evidence artifacts; the stub binds its own diagnostic artifact through the runtime API. | The gate's conformance checks are proved for the core's handling of evidence; they say nothing about the wrapper producing it. |
| 5 | **Profile `requests` and `tokens` controls are not qualified.** The gateway enforces the project's settings limits, not an allowance a profile claims, so the catalogue tuple qualifies `model`, `tool_calls`, `tool_allowlist` and `transcript`, and a profile claiming `maxRequests` is refused (`profile_unsupported`). The request and token ceilings are proved through project settings. | AR-02 holds as "unqualified controls are refused"; a per-profile allowance is future work. |
| 6 | **The build is deterministic and republishes an image**; kind pulls it through the registry mirror. No code is compiled. | The registry verifier, digest reuse and the deployment record are real; build correctness is not claimed. |
| 7 | **An explicit cleanup request of an already cleaned deployment** answers `200` and admits no run (logged by `TestDeliveryAssemblyReplay`); the suite asserts the idempotence, not that status. | None. |
| 8 | **Test-environment tuning**: the startup budget is four minutes, the cleanup sweep two seconds, preview TTLs the API minimum of 60 seconds; all selected through the installation statement, none in product code. | None. |

## What this does not claim

Live-provider, wrapper-image and OpenCode behavior (T-085); the Kubernetes runtime, the chart and the restricted baseline (T-089); release acceptance (T-090). The deterministic agent stands in for a harness only at the wire the control plane sees. The kind cluster is the preview's deployment target only: no workload of the platform runs on it. The gateway and proxy keep their own T-032/T-033 suites and the delivery scripts their T-065/T-067 suites; this report claims their behavior only as joined through the assembled core.
