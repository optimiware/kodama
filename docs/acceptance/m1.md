# M1 integrated acceptance (T-026)

This is the reproducible report of the M1 checkpoint: the actual core assembly (`internal/app`, `KODAMA_ENV=test`) driven only through its public client and CLI over the services of the `test` environment ([ADR 0009](../adr/0009-environments.md)): `DEV_STACK=services`, the Podman runtime, real PostgreSQL, JetStream, S3, Git and OIDC, no cluster. The installed chart, kind and the Kubernetes runtime belong to T-089. Nothing here is a production, cloud-KMS or live-model qualification.

**Status: every scenario below passes** against the tree that includes the repair of finding 1 (the workspace-free dispatch defect in `internal/execution`), which this checkpoint found and which the branch now carries.

### Fixture notes

* The data path has only test-owned TCP proxies in front of PostgreSQL and NATS (to sever and restore them) and a forward proxy for the object store. The server signs upload URLs with its configured S3 endpoint and hands them to the workload, so the endpoint is the name a container resolves (the scope's LocalStack on the workload network); the host-run server reaches it through a forward proxy (`HTTP_PROXY`, which Podman is told not to copy into containers). `net/http` reads the proxy settings once, at its first use, so the first test process only hosts the forward and re-runs the test binary as a child whose environment names it (`kit.Main`); the child verifies the proxy is in effect before any test runs.
* A container reaches the runtime API through a TLS front on the host that forwards only `/runtime/v1/` to the running process, so a workload never reaches the public API. The front outlives server restarts; its origin is the runtime tokens' issuer.
* When the user's kernel key quota is nearly spent (every running container holds one of the 200 keys of `kernel.keys.maxkeys`, which a host running several scopes can exhaust) the suites create containers without a session keyring (`CONTAINERS_CONF_OVERRIDE`). It changes nothing a test observes and is reported on stderr.

## Findings

Product defects the integrated path found. Product bugs return to an explicitly assigned owner before acceptance passes; this task owns only tests, this report and `openforge.json`.

1. **Repaired (found by this checkpoint): a work run's workspace-free step could not be dispatched (`internal/execution`, T-080/T-020).** `claimMutation` passes `Workspace: run.WorkspaceID` to `Aggregate.Claim` for every step, while the attempt row requires `access = 'none'` to have no workspace (`step_attempts_workspace_shape`). The memory adapter has no such constraint, so only PostgreSQL refuses: every claim of an `access: none` step of a work run fails and the run never starts. The Podman runtime runs only workspace-free attempts (ADR 0008), so no container step of a work run starts on the `test` environment. The repair now in the tree (without it every container scenario in this report fails at dispatch):

   ```diff
   --- a/internal/execution/dispatch.go
   +++ b/internal/execution/dispatch.go
   @@ func (s *Service) claimMutation(stepID string, src SourceInfo, lim Limit) Mutation {
   -		at, err := agg.Claim(ClaimParams{
   -			StepID: step.ID, AttemptID: attemptID, Plan: plan, Access: binding.Access, Workspace: run.WorkspaceID,
   +		// A step that consumes no source is bound to no workspace: the attempt's
   +		// shape (step_attempts_workspace_shape) is all-or-nothing.
   +		workspaceID := run.WorkspaceID
   +		if binding.Access == AccessNone {
   +			workspaceID = ""
   +		}
   +		at, err := agg.Claim(ClaimParams{
   +			StepID: step.ID, AttemptID: attemptID, Plan: plan, Access: binding.Access, Workspace: workspaceID,
   ```

   Remaining follow-up for the owner of `internal/execution`: a unit test over the memory adapter (the shape is a database rule the memory store must also enforce).

2. **Worked around in the fixture: the assembly does not create its spool directories (`internal/app`, T-027/T-070).** `NewCore` configures `<scratch>/artifact-spool` and `<scratch>/log-spool` but nothing creates them, so every artifact completion (the wrapper's log upload included) answers `503 unavailable` (`os.CreateTemp` on a missing directory) and no log is ever retained. The fixture creates both directories, as an installation must until `NewCore` does.
3. **Worked around in the tests: a declared file output is reserved under its file's base name, but the artifact service requires the declared output name (`internal/entrypoint` T-016 vs `internal/artifacts` T-023).** A step declaring `report: {type: artifact, path: /kodama/outputs/report.txt}` is refused (`422 output_invalid`) and the attempt fails. The tests declare the output with a file whose base name equals the output name (`report`), where the two agree.
4. **Classification is coarse: an `output_invalid`/`output_upload_failed` result is recorded as `command_failed` (`internal/results`, T-022).** The attempt still fails, no outputs are exposed and diagnostics stay readable (PX-A07 holds); the finer reason is lost to the API reader. The tests accept either reason.
5. **Stale integration suite: `test/integration/assembly-core` (T-070) no longer compiles into a working run.** It builds `app.CoreConfig` without `Env` and asserts that nothing dispatches, both false since T-071. It is not owned by this task and is not part of its check; this suite and `TestM1Tracer` supersede it. Owner: T-070/T-027.

## Known limitations

* **No source checkout or publication from a container outside Kubernetes in this recorded run.** At this checkpoint, the Podman runtime refused an attempt that consumes the workspace (`bootstrap.ErrNoCheckout`, ADR 0008); later T-098/T-101 added and bound checkout support for separate qualification. All container steps of this report are workspace-free. The writer's reservation, expected tip, revocation and the human-push compare-and-swap are exercised against the real workspace service and Git remote, but the publication of a writer's bundle by a running attempt (WS-A03 publication, WS-A05 uncertain push of a bundle, WS-A06 recovery from the published commit, WS-04/06/11 in the callback path) belongs to the T-022 integration suites and the planned T-104 Kubernetes `kube_m1_roundtrip`, not this run.
* **Kubernetes evidence has two owners under O-24:** T-089 retains IT-A06 (restricted Pod baseline, NetworkPolicy, quota), component forms of PX-A02 (adoption after a lost create acknowledgment)/PX-A06 (cancellation during create), and chart installation/configuration refusal. T-104 retains full assembled forms and installed-server readiness. The Podman runtime does not enforce a tenant network policy or aggregate quota; `PX-A04`'s quota ordering is covered at the unit and contract layers.
* **Runtime identity and keys are development custody:** the keyfile KMS (explicitly acknowledged), the runtime signing key generated per stack, the OIDC fixture and plain-HTTP object store are the `test` environment's adapters, never production's (SD-12).
* **Recovery boundaries not injected:** a lost response to the container create call and a crash inside a database transaction are decorated faults of the unit and `execution-composition` suites; here the process, the database, the broker and the object store are severed and restarted from outside.
* **Host dependencies:** the suites need a rootless Podman engine that lets a container reach `host.containers.internal` and the scope's network, and at most the kernel key quota workaround above. They do not run in the unit layer and are not part of `make test-go-unit`.
