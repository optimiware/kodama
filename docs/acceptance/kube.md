# Kubernetes runtime and chart component conformance (T-089)

This is the report of the **component checkpoint** of the `production` environment on kind ([ADR 0009](../adr/0009-environments.md), [environments](../implementation/environments.md) step 6) as scoped by owner decision O-24: the real Kubernetes runtime, its restricted baseline, and the real chart installed with `KODAMA_ENV=production` and observed to refuse invalid production configuration. It ran on the `cluster` stack after M1 passed on Podman ([m1.md](m1.md)) and after T-095 (stopped/removed `Start` conflict) and T-102 (O-25 launch-evidence capability). It is local conformance, not stage deployment (T-090) and not cloud-KMS, hosted or production qualification.

**Status: the component checkpoint passes** (`kube_runtime_contract`, `kube_component_roundtrip`, `kube_component_cancel_restart`, `kube_restricted_baseline`, `kube_chart_fail_closed`). **It is not full Kubernetes M1 closure.** A correct startup refusal is not a working installation: no installed server became ready and no assembled-server roundtrip ran on Kubernetes. Those obligations keep their original names, `kube_m1_roundtrip`, `kube_cancel_restart` and `kube_chart_install` (including T-026's three backend-parameterized `execution_assembly_*` scenarios), and belong to [T-104](../tasks/T-104-kubernetes-full-readiness.md) after the production key wiring (T-029), HTTPS dependencies and T-103's cleanup. Nothing here is skipped or weakened.

## Running it

```sh
make dev-preflight DEV_SCOPE=t089            # read-only: endpoints, cluster readiness (cluster stack)
make check-go-integration PKGS=./test/e2e/kube/...
```

`check-go-integration` provisions a missing scope (the default `cluster` stack), preflights it and loads `host-env.json` before the tests. The tests fail, never skip, when the cluster, PostgreSQL or the scope is missing (`TestMain` sets `KODAMA_REQUIRE_KUBERNETES`, `KODAMA_REQUIRE_POSTGRES` and `KODAMA_REQUIRE_S3`) or when the scope is not the `cluster` stack. Wall time on the recording machine: about 5 to 6 minutes for the whole package (first run adds the one-off Helm download and image builds).

## What is real and what is not

The runtime under test is the genuine `internal/kube` runtime, Job observer, planner and reconciler over the real cluster API, driven by the real `execution.Service`, the real runtime-admission service (`internal/runtimeauth`, JWT tokens, PostgreSQL grants) and the real `kodama step` entrypoint running in the Pods. This is the component stack of `test/integration/kube` (T-021), run here as the acceptance of the Kubernetes backend.

**It is not the assembled server, and no test here claims it is.** The injected control-plane and callback dependencies are, exhaustively:

| Injected | Stands for | Where |
| --- | --- | --- |
| `executiontest.Env`: one PostgreSQL database per stack migrated with the execution, runtime-admission, identity, secrets, pipeline and workspace modules | the assembled server's store wiring | `stack_test.go` |
| The runtime API server: the real `runtimeauth` HTTP handler behind a TLS listener on the host that Pods reach through the provider's host address, with a **result route stand-in** that authorizes through runtime admission and commits through `execution.CommitResult` | `/runtime/v1` of `internal/app` and the results service (T-022/T-062); not evidence of assembled result finalization | `stack_test.go` |
| `FakeSources` (Git observation) and `FakeEffects` (the effect reconciler's verdict, set explicitly where a test needs trusted evidence) | workspace and delivery effect adapters | `executiontest` |
| `sqlWork`, `allowCleanup`, the fault-injecting cluster wrapper | the work reader, the cleanup authorizer, and the lost-acknowledgment/delete faults | `stack_test.go`, `helpers_test.go` |
| `boundRuntime` (contract test only): binds each contract spec to a real admitted and claimed attempt and performs three duties ADR 0008 leaves to execution above the seam, as `execution.Service` does: binding the instance UID after a start (`drive`), committing the cancellation before a never-started workload is stopped, settling the attempt before its workload is removed | the execution service above the runtime | `contract_test.go` |

`KODAMA_ENV=production` refuses every fixture the scope provides (the development key file, the plain-HTTP LocalStack object store and OIDC issuer) and until T-029 has no cloud key provider to select, so `app.NewCore` cannot start under `production` on any local scope. The suite therefore proves the construction guard on the real runtime set (`production guard`: production admits the Kubernetes runtime, observer and planner and refuses Podman) and proves the chart's server refuses to start, instead of composing the server. There are no artifact uploads, workspace checkouts or retained logs in this stack.

## Findings

The first run of this checkpoint (before T-095 and T-102) found two deviations of the Kubernetes runtime from the shared contract, now repaired by their owners and no longer findings: a start of a stopped or removed workload returned `kube.ErrNotDispatchable` instead of `execution.ErrConflict` (T-095), and the contract demanded `LaunchNotStarted` after stopping a never-started workload, which Kubernetes cannot prove from missing records (O-25, T-102). The same first run established that no production server can start locally; that is now the scoped, tested refusal of `kube_chart_fail_closed` and T-104's prerequisite, not a defect of this task.

1. **Observation, no action requested: an evicted workload is recorded as a command failure.** When the kubelet evicts a Pod for exceeding a volume limit, the attempt is recorded as `failed`/`command`/`command_failed` (the entrypoint reports the termination before it dies) rather than an infrastructure failure. The run never succeeds and no output is exposed, so `storage is bounded` holds; the finer reason is lost to the API reader, as findings 3 and 4 of [m1.md](m1.md) already record for upload failures.
2. **Observation: stop before start is fenced by committed state.** The Kubernetes runtime fences a start after a stop through the committed attempt (cancellation/revocation) and its own record, as its T-102 tests do; a bare `Stop` with neither fences nothing. Execution always commits the cancellation first, which `boundRuntime` reproduces; the contract does not require more of a backend.

## Known limitations

* **Component stack, not the assembled server** (see above). `internal/app.AssembleExecution` and `NewCore` are not run under `production`; the construction guard is proven on the real runtime set only.
* **Not repeated on Kubernetes:** artifact upload and verification (PX-10), retained and live logs through the log API, source checkout and publication by a workspace-consuming attempt (WS-A03, WS-A05, WS-A06) and the runtime API's real result route. They need the assembled server (T-104); the Kubernetes runtime's own checkout credential path is covered by T-079's unit and `test/integration/kube` evidence.
* **Tenant isolation between namespaces** is shown by the default-deny policy (a reachable host port is closed from inside the Pod) and by the service account's lack of cross-namespace permission; no cross-tenant Pod-to-Pod probe is made because every tenant Pod's own ingress is denied too, so such a probe would not discriminate the egress policy from a missing listener.
* **Default CNI.** NetworkPolicy enforcement is that of kind's kindnet; another CNI is not qualified here. `kube_restricted_baseline` fails if the CNI does not enforce the policy.
* **One node, one control plane, one replica**, rootless Podman as the kind provider. No upgrade, multi-replica, node-loss or Pod Security version-skew behavior is exercised.
* **Chart profile.** The chart is installed with the `development` profile adapted to the scope (in-cluster `kodama-deps` endpoints, the scope's fixtures as Secrets, the kind subnet as the policy's egress destinations, a placeholder https runtime origin that nothing calls), once with the AWS key provider selected (no key file projected) and once with the development key file, whose refusal is the assertion. `values-external.yaml` cannot be installed locally: it names cloud KMS and external endpoints.
* **Development custody.** Every secret in the install is a scope fixture; the development key is only ever selected to be refused. None of this is a production, cloud-KMS or hosted qualification (T-029, T-061, T-056).
* **Host dependencies:** a container provider reachable by kind, kind and kubectl from `make tools`, network access once to download the pinned Helm (or `KODAMA_HELM`), and free memory for one kind cluster.
