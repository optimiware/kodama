# internal/integrations/gitwebhook

Native Git push trigger (task T-036, decision O-03): a server-side `post-receive` hook on a Git host the installation controls sends an authenticated notification; Kodama verifies it and starts a run for the exact announced commit. HTTP contract and wire format: [`api/git-webhooks.yaml`](../../../api/git-webhooks.yaml). Example sender: [`example/post-receive`](example/post-receive).

**Status.** Implemented and unit-tested against in-memory persistence and Git/admission doubles. It is **not wired**: nothing registers the route, a PostgreSQL store, the real `workspace.RefReader` or `execution` admission yet. T-038 owns that join (`native_hook_roundtrip`) and real Git/persistence behavior. Management use cases (`Install`, `SetEnabled`) are Go-level; their HTTP exposure belongs to the assembly that owns identity routing.

**What this is not.** No Git server or transport, no GitHub/provider adapter, no universal provider abstraction, and no payload field is ever executed or used as a URL, path, tenant or credential.

## Trust model

| Input | Authority |
| --- | --- |
| Trigger ID in the URL | An address only. |
| `Kodama-Signature` | HMAC-SHA256 under the trigger's hook secret over `trigger ‖ delivery ‖ timestamp ‖ SHA-256(body)`; ±5 min clock window. |
| Tenant / project | Only the trigger record. The payload cannot carry them (unknown members are rejected). |
| `repository` member | A claim checked against the trigger's bound repository; the project's *current* repository must still equal it. |
| Commit | Announced by the hook, then proved on the remote: branch exists and its history contains it, read with the project's **read-only checkout credential**. The tip is never used; branch movement cannot change the run's commit. |
| Run authority | The installing principal's current `ActionRun`, re-checked every delivery. The hook secret is not an identity. |

The hook secret must be a dedicated secret (≥32 bytes), never the checkout or publisher credential; the publisher reference is never offered to the Git port.

## Delivery

Order: authenticate → parse → **durable claim** `(trigger, delivery id)` → replay a finished record → repository identity → branch filter → current repository binding → installer authority → exact commit on remote → `BeginAdmission` → admission phase → finish with audit. A forged request never reaches the claim, so it cannot burn an identifier. Every terminal result of an authenticated, well-formed delivery (started, ignored, or any refusal) is persisted atomically with its audit, so the identifier is deduplicated whatever the outcome: replay returns the recorded result (even through repository changes or outages), and the same identifier with another body is `delivery_conflict`. A dependency outage leaves the claim pending and the retry resumes it.

**Admission phase and fences.** `BeginAdmission` durably marks the delivery `Admitting` before the first admission attempt; from then a run may exist. The phase first recovers a run already admitted under the idempotency key `git-hook:<trigger>:<delivery>` (`Runs.FindRun`), with no authority or branch re-check, so a lost response or lost finish followed by installer revocation or branch movement still yields the actual run and its `run_started` audit. To create a run that does not exist, the processor must hold the delivery's **admission lease** (`Store.AcquireAdmission`, `AdmissionLease` = 2 min, `StartRun` bounded to 30 s). Only the holder calls `StartRun` or records a refusal, so success and refusal are mutually exclusive durable outcomes: a competing processor gets `ErrAdmissionBusy` (an `ErrUnavailable`, HTTP 503, retry) and the store rejects a refusal finish from a non-holder. **Refusal ledger.** A refusal is first decided in admission's own ledger (`Runs.DecideRefusal`, atomic with run creation for the key): if a run exists it wins and is recorded as `started`; otherwise the refusal is made durable (first reason wins) and `StartRun` for that key then creates nothing and returns `ErrAdmissionClosed` — even for a holder that stalled before its call, lost its lease, and resumes after a replacement recorded the refusal. The delivery records a rejection only from that ledger result, so a rejected delivery can never acquire an unrecorded run, and a lost finish replays the same reason. Under the lease the project's current repository is re-checked (a rebound project is a recorded `repository_rebound` refusal, never a new run) and the verified `RepositoryID` is carried in `RunRequest` so admission can preserve and enforce it. A processor that fails non-terminally releases the lease at once; a vanished holder delays others only until expiry. The lease only limits contention; correctness against a stalled holder rests on the ledger. T-038 must implement `StartRun`/`FindRun`/`DecideRefusal` over one admission store with that atomicity (idempotent by key, refusing a conflicting `RepositoryID`). A pre-admission result (ignored/rejected) cannot be recorded for an `Admitting` delivery; that processor joins the admission. Filters are explicit (`main`, `release/*`; never "all").

## Persistence seam

`Store` (ports.go) owns triggers, delivery records and audit, writing audit in the transaction of the change. `gitwebhooktest.Store` proves policy only (uniqueness, first-finish-wins, optimistic version). A PostgreSQL adapter must give `ClaimDelivery` a unique `(trigger_id, delivery_id)` key and decide a retention horizon for delivery records (not chosen here: records are kept).

## Audit

`git_trigger.installed|enabled|disabled`, `git_hook.authentication_failed` (known triggers only; unknown triggers have no tenant to attribute), `git_hook.rejected`, `git_hook.ignored`, `git_hook.duplicate`, `git_hook.run_started`. Records carry delivery ID, ref, commit, run and a stable reason; never signatures, bodies or secrets. Refusal audits are best effort; the `run_started`/`rejected` outcome audit is atomic with the delivery record. Rate limiting of unauthenticated traffic is an edge concern of the assembly.

## Native triggers of the internal Git service (T-137)

The sections above describe the **external** receive-hook trigger (HMAC, `git_triggers`); it is unchanged (`Test_unit_trigger_external_hmac_unchanged`). The files `native_*.go` add the triggers of the internal Git service ([ADR 0011](../../../docs/adr/0011-internal-tenant-git-service.md), [Git repositories](../../../docs/specs/git-repositories.md#triggers), [Git service contract](../../../docs/contracts/git-service.md#trigger-configuration), PX-24, GR-10, GR-11, GR-A07). HTTP shapes: [`api/git-triggers.yaml`](../../../api/git-triggers.yaml) (not in the aggregate until T-158). **Not wired**: the event subscription, routes and composition are T-132/T-158's; nothing here is registered in `internal/app`.

**Push triggers.** The consumer takes the reference-only `git.refs_updated` envelope (validated with `eventsv1`; aggregate `git_push`, project required). For the project's *enabled* triggers of the event's repository: a run-originated push (`originRunId` not null) is skipped from the event alone for a trigger that excludes origin runs (the default), **before the record is reloaded** (no reload at all when every trigger excludes it); otherwise the record is reloaded by `pushId` (scope and repository compared; it must be applied) and, per trigger and entry, only an **applied, non-delete** entry whose ref matches a pattern is admitted. The record's own `originRunId` is authoritative too. The run pins the entry's `new` commit (`gitv1.PinnedCommit`), never a tip; `SourceRunRequest` carries it as `ExpectedCommit` and `adapters.NativeRuns` verifies the admitted run's pinned entry equals it. Push runs have no work item, content revision or workspace.

**Deduplication and recovery.** One inbox row per `(trigger, push record, ref)` (`git_trigger_inbox`, primary key = the claim) and one stable run ID derived from the key (`InboxKey.RunID`, so the key also is the run identity: execution's own idempotency, the same run ID with the same declaration is a replay and another declaration a conflict, is the at-most-one guarantee). The claim carries a lease that only limits contention (`ErrAdmissionBusy` is retryable). Order: claim → **recover a run that already exists** (`SourceRuns.Find`, no authority or source re-check, so a lost response or lost outcome record followed by revocation still ends as `started`) → admit → record the write-once outcome with its audit atomically. A permanent refusal (`ErrRunRefused`) is recorded as `rejected` only if no run exists (the run wins), then replayed forever; quota, busy and infrastructure failures are `ErrUnavailable`: the claim is released and the redelivered event resumes the same key. **Lease fence (the refusal window).** Every attempt is its own lease holder (`<Holder>#<n>`), and the store records a non-started outcome (`rejected`, `ignored`) only for the holder of the lease *while it is still valid*; a `started` outcome needs no lease. A stalled attempt whose lease lapsed, or was taken over, therefore cannot record a refusal while another attempt may be creating the run: its write is `ErrConflict`, which the consumer reports as `ErrAdmissionBusy` (retryable), and the redelivery recovers the winner's decision (`started`). What remains is a refusal recorded by a holder that still holds a valid lease while a run appears for the same run ID from outside the native path (nothing else creates native run IDs); the run's existence wins on every later read (`Find` before every attempt), so such a key is explained by its run, never silently lost. An admission slower than the lease (`DefaultInboxLease`, 2 minutes) ends in the retryable busy error, not in a wrong decision. The external ledger tables are untouched; the native path has its own because its run identity, not a refusal ledger row, makes admission idempotent.

**Refusal reasons and status.** A permanent refusal records a stable, sanitized reason code (`gitwebhook.RefusalCode`; `adapters.NativeRuns` derives it from execution's sentinel or its stable leading admission code, for example `run_authority_denied`, `work_item_not_actionable`, `source_set_push_repository`), never a message, name or secret; anything else is `admission_refused`. `NativeConfig.TriggerStatus` and `TaskRouteStatus` (read authority; `getGitTriggerStatus`, `getGitTaskRouteStatus`) return the configuration with its last decision and last refusal, so a configurer without run authority sees why every start is refused. Configuring still needs only `ActionInstall`: no new authority is required, and the refusal shows at the first push.

**Enablement instant.** `EnabledAt` is set when a trigger or route is created enabled or re-enabled (not by other alterations). An event whose envelope `occurredAt` (the settlement commit of the push record, or the readiness transition) is **before** it is ignored without a claim (`event_before_enabled`), so a late redelivery cannot start runs for pushes the configuration was not yet watching, and a re-enabled trigger does not replay its disabled window. The record's own `createdAt` is the receive's authorization time, not its application time, so the event's time is the reliable one; clock skew between producer replicas is the only limit (an event within that skew of the instant is treated as after it).

**Retention.** Inbox rows are kept: the runtime role has no `DELETE` and a decided key is final, because the decided row is what stops a redelivered event from starting its run again. Cleanup is an owner-role maintenance action, not part of the request path, and belongs with the retention and maintenance work of T-138 (`internal/gitops`), scheduled by T-132's composition; no horizon is chosen here. Any horizon must exceed the longest redelivery window of the event stream (its maximum age plus redelivery backoff), because deleting a decided row re-opens its key.

**Task route.** One enabled route per project (`TaskRoute`: definition, `ConfiguredBy`). `work_item.transitioned` to `ready` or `work_item.created` in `ready` claims `(project, item/transition)` and then reads the item's *current* state: not ready, blocked, cancelled, not actionable or vanished is a recorded `ignored`; otherwise a `work_item` run pinning the current content revision is admitted through the same `SourceRuns`. Leaving and re-entering `ready` is a new transition and a new run. Current authority (`ConfiguredBy`), quotas, cancellation and run idempotency are admission's; business WIP is the work module's rule on the ready-to-active edge and is never bypassed.

**Authority.** `NativeConfig` authorizes every call with the injected `Authorizer` (`ActionInstall` for create/alter, `ActionView` to read; a hidden object is `ErrNotFound`, an outage is never access). Creation checks that the repository is internal and not archived (`ErrHostingMismatch`, `ErrRepositoryArchived`) and the definition registered; the repository binding is immutable; there is no delete (a trigger is disabled). The principal who created or last altered the configuration is `ConfiguredBy`, and admission checks *their* current run authority on every start.

**Persistence.** `git_push_triggers`, `git_task_routes`, `git_trigger_inbox` (migration `012_git_triggers.sql`): composite ownership keys to project, repository and definition, forced tenant row level security, version/identity guards for every role, no `DELETE` grant, audit in the transaction of the change. `postgres.NativeStore` runs `gitwebhooktest.NativeStoreContract` (`TestPostgresNativeStoreContract`) beside the memory store; `TestPostgresNativeMigration` and `TestPostgresNativeIsolation` prove ordering, constraints, grants, isolation and the guards on real SQL.

**Acceptance.** `Test_unit_trigger_dedup_by_push_and_ref`, `Test_unit_trigger_excludes_origin_run`, `Test_unit_trigger_exact_pushed_commit`, `Test_unit_trigger_without_work_item`, `Test_unit_trigger_repository_and_ref_filters`, `Test_unit_trigger_configuration_authorized`, `Test_unit_trigger_task_ready_admission`, `Test_unit_trigger_external_hmac_unchanged` (GR-10, GR-11, GR-A07, PX-24, PX-A20), plus the store contract, the adapter tests and `Test_unit_trigger_api_fragment_matches_contract`.
