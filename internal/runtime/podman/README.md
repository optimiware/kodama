# Podman runtime

`internal/runtime/podman` runs attempt workloads as Podman containers: the step's digest-pinned image on a read-only root filesystem, all capabilities dropped, under CPU, memory and process limits. It is the local end-to-end backend ([ADR 0008](../../../docs/adr/0008-runtime-seam.md)); it does not enforce tenant network policy or quotas.

## Source checkout (T-098)

Checkout is supported when a `bootstrap.CheckoutProvider` is configured on `podman.Entrypoint.Checkout`; without one, an attempt with `workspace.access: read|write` is refused with `bootstrap.ErrNoCheckout` and no container, admission credential or file is created. This is the Podman equivalent of `kube.CheckoutProvider`; the composition (T-101) supplies the provider.

For a source-consuming attempt the runtime asks the provider once per container create, with the committed attempt's scope, workspace and the repository and commit its pinned context names. The provider answers only for that repository; a refusal (`bootstrap.ErrCheckoutDenied`) or an answer that does not echo the request's scope, workspace and repository, that is not one `username:password` line, or whose Git CA is not a certificate bundle, is a definite refusal. Any other provider error is an outage: nothing is started and the dispatch is redriven.

The credential and the Git CA are written (mode 0600) as `checkout-credential` and `git-ca.crt` into the attempt's bootstrap directory, which is bind-mounted read-only at `/kodama/bootstrap` and removed with the workload. The entrypoint is pointed at them with `--checkout-credential-file` and `--git-ca-file`. They are never environment variables, arguments, labels or image content. A workspace-free attempt receives neither file and does not consult the provider. The writer's publisher credential is never requested or delivered: publication stays on the workspace service. An adopted container (a restart or redrive) never consults the provider again.

## Launch evidence (T-102)

Podman declares `Capabilities.ProvesNeverStarted`: the durable record is written before any container exists, so a `Stop` before the start is fenced (a later `Start` is `ErrConflict`) and affirmatively reports `LaunchNotStarted`. The declaration is launch-history proof only and separate from the container guarantees. The shared `runtimetest.Contract` requires it of Podman and of the Process runtime; the real-engine run stays with the integration checkpoint.

## Run resources (T-115, P5 of the run-workspace plan)

`podman.Resources` implements `execution.RunResources` ([run resources](../../../docs/contracts/run-resources.md), seams S1–S5 of the [implementation plan](../../../docs/implementation/run-workspace-services-builders.md#integration-seams-frozen-by-t-122)) with Podman objects: a run **network**, a run **volume**, one **preparation** container and **service** containers. Under O-30 Kubernetes is the delivery backend; Podman gives lifecycle evidence and refuses what it does not enforce. Local evidence never certifies Kubernetes.

| Resource | Podman object | Identity |
| --- | --- | --- |
| `network` | `--internal` bridge named `kr-…` | network ID + instance UID label |
| `workspace` | named volume `kr-…`, mounted `:U` at `/workspace` | creation time + instance UID label |
| `preparation` | container running `/kodama/bin/kodama prepare` from the injected binary, in the policy-pinned image | container ID + instance UID label |
| `service` | container of the declared image and argv (or `service-run -- argv` when it has secret bindings), network alias = the contract's endpoint host | container ID + instance UID label |

**Durable fence.** `StateDir/resources/NAME/record.json` is written before the object exists (with the instance UID the adapter generates) and kept as a tombstone after removal; a stopped or removed name is `ErrResourceFenced` forever, a stop before the create fences a late create, and an engine object without our record, with other labels, another UID or another engine identity is a collision that is never adopted, stopped or removed. Containers are acted on by verified ID, never by name. `podman X exists` exit codes 0/1 are the only evidence of presence/absence; any other failure is `unknown`, never `absent`, and never a confirmed stop or removal.

**Attempts (`AttemptSpec.Shared`).** `Config.RunResources` enables run_shared launches. The Runtime verifies the run's volume (record, labels, bound UID), mounts it read-write at `/workspace` (never a tmpfs), runs the attempt as the installation's non-root workload user on the run network (plus `Config.Network` if set), applies only the pinned step role (all capabilities dropped, then `capabilitiesAdd`; no-new-privileges exactly when none is added) and refuses a role field it cannot enforce (a non-`nonroot` user, host user namespace, Localhost seccomp, LSM profile, devices, unmasked `/proc`, a capability beyond `SETUID`/`SETGID`). `podman.Entrypoint` adds `KODAMA_RUNTIME_API=v2` and never a checkout credential for such an attempt. The workspace lock is held across the launch, so `Stop` of the workspace waits for a create and a create after a confirmed stop is fenced; the volume is `Released` only when no container (running or created) still references it, and `Remove` never forces.

**Admission credentials (S5).** `ResourcesConfig.Registrar` is a consumer-owned `ResourceRegistrar` with an adapter-local `ResourceRegisterCommand`; the composition (T-116) bridges it to `runtimeauth.Service.RegisterResource`. The credential is generated, persisted in the workload's bootstrap directory and only then registered; a retry or restart registers the same value, and the files are destroyed at stop. The bootstrap mount is `0644` in a `0755` directory because the non-root workload user cannot read files its host owner made `0600`; confidentiality rests on the `0700` resource directory above it.

**Advertised capabilities** (`podman.ResourceCapabilities`): `run_workspace`, `workspace_fence`, `workspace_preparation`, `resource_recovery`, `run_services`, `service_isolation` — each held by the fake-engine program assertions and the real `make test-podman` roundtrip. **Not advertised:** `run_network_isolation`, `declared_edges`, `named_egress`, `egress_default_deny` and every builder member (an internal bridge is not an owned filtered egress path and is not traffic-tested against foreign runs); the attempt runtime still lacks `network_policy`, so no `run_shared` admission accepts Podman today.

**Not supported (refused before any effect):** `http` readiness, `tcp` readiness without `ResourcesConfig.ProbeImage` (an image with `nc`; the probe runs on the run network through the endpoint alias), a secret-bound service without a declared command, a preparation without `EntrypointBinary`, `ControlNetwork` or a `Checkout` provider. No container gets the host engine socket; services join only the run network, and only preparation and secret-bound services also join the control network.

`make test-podman` runs the exported `runtimetest.RunResourcesContract` and a multi-image volume/service roundtrip (alpine and BusyBox attempts sharing one volume, a service reached through its alias, a restarted adapter, cancellation and a leak check) against the real engine.

### Review hardening

- **Announced creations, no inference, no placeholders.** The creation of every engine object is recorded before the engine is asked, and the request is counted unanswered; the answer is recorded in one write together with the identity of the object it made, so a request is never counted twice. **At most one request is ever in flight for a name:** while one is unresolved, Ensure issues no other. Nothing turns an outstanding request into evidence by time, a client clock or an engine uptime, and the adapter never creates or deletes a placeholder to settle it. An unresolved request (its answer was not seen and its object is not observed) keeps the resource conservatively unresolved: Observe reports `unknown` (reason `create_unresolved`), Stop is not confirmed (`stopped: false`, launch `unknown`), Remove is refused (`cleanup_pending`) and a workspace is not released while one of its holders is unresolved. It resolves only (a) when the object is observed — found by name and ours, however late it lands — and is then adopted, stopped and removed like any other object, or (b) by an explicit, durably recorded operator retirement. A request that lands after cleanup was attempted is therefore still cleaned up, and removal is never confirmed while it could still land.
- **Operator retirement of an unresolved request.** If the request will never be observed (the engine never received it, or the object it made was deleted by hand), the run stays visibly non-terminal until an operator acts. **Procedure:** (1) make sure no creation request for the resource can still reach the engine (for a remote engine: restart the engine host and stop any client of this installation that might still be running a request) and check with `podman ps -a`, `podman volume ls` and `podman network ls` that the engine holds no object of that name that belongs to the run (if one exists the adapter finds and cleans it by itself; an object of that name that is not ours is a collision and is never touched); (2) call `podman.RetireUnresolvedRequest(stateDir, name)` with the resource name (`kr-…`): the name of the run workspace also covers every unresolved holder marker of that workspace, and a service's name covers its probe container. The adapter records it durably and then treats the outstanding requests as retired, so Stop and Remove complete when nothing of ours exists. It is the operator's assertion: an object a retired request creates afterwards is not tracked, and a retirement never hides an object of ours that exists. Each retirement advances a per-name epoch and covers only the requests and holder intents announced before it, so a create issued afterwards is a new unresolved request. Only the genuine absence of the epoch file means no retirement; an unreadable or malformed one blocks every new create and every retirement decision (the resource stays unresolved, calls report unavailable and are retried) until it is fixed, and `RetireUnresolvedRequest` refuses to write over it.
- **Workspace holder intents.** A preparation or attempt that will use the run volume is recorded, under the workspace's lock, before its create is issued (`resources/<workspace>/holders/`), and the marker survives an ambiguous answer and restarts. An unresolved holder means the workspace is not released and not removed; it resolves when the container is found and bound (it then holds the workspace until it is stopped and removed) or by the operator retirement for the workspace name. A foreign object that holds the container's name settles nothing: the intent stays and the workspace stays held. A shared attempt has at most one create in flight too: a redrive of `Start` over an unresolved create adopts the container if it is observed (binding the holder) and otherwise returns `ErrUnavailable` without issuing a second create, so the marker is never rebound to a replacement; after delivery the redrive adopts the first container.
- **tcp probe containers** are created by a recorded intent (a per-service nonce label, the deterministic name `<resource>-probe` serializing probes), bound by the ID the create returned, started attached and deleted by that bound ID only. An outstanding probe create is resolved by the name with the nonce (then deleted by the ID found) or by the operator retirement for the service name, and keeps Stop and Remove unconfirmed meanwhile; a replacement that copies every label, or a foreign container at the name, is never deleted.
- **Workspace release** is decided from the verified volume instance (labels, UID, creation time) and the containers that reference it; a replaced or uninspectable volume is a collision or an error, never a release.
- **Stop intent vs stop.** `Stopping` is the fence; `Stopped` is recorded only after the stop is verified, `Remove` requires it, and Observe reports `pending`/`resource_stop_unconfirmed` while a container still runs.
- **User namespace.** A role with `userNamespace: pod` — and every preparation and service container — runs with `--userns=auto`; the engine's annotation and ID mapping are verified on the created container before it starts, and a container the engine did not isolate that way is removed, never started. A role that adds capabilities without a user namespace is refused. Real-tested against the local rootless engine (the attempt's `/proc/self/uid_map` differs from the default namespace's).
- **Lost records.** A stop or remove of a resource nobody recorded leaves a tombstone that keeps the identity the caller supplied (`untracked`, launch evidence `unknown`).

## Kernel runtime contract (T-177)

`KernelRuntime` and `KernelResources` implement the `internal/kernel/runtime` ports `Runtime` and `ResourceManager` over Podman ([ADR 0008](../../../docs/adr/0008-runtime-seam.md), [ADR 0010](../../../docs/adr/0010-run-workspace-services-builders.md)). They are separate from the legacy `execution.Runtime`/`RunResources` adapters above (which keep their behaviour and tests) and are not wired by `internal/app`. Their sources (`kernel_*.go`) import only the standard library, `internal/domain` and the kernel contract; `Test_unit_podman_kernel_adapter_boundary` enforces it.

- **Workload.** The step's digest-pinned image (an unpinned image is refused) as uid/gid 65532, read-only root filesystem, all capabilities dropped, `no-new-privileges`, CPU/memory/PID limits, the declared timeout as `--timeout`, `/tmp` in memory. The run workspace volume is mounted at `/workspace`; private secrets, when materialized for the step and run, read-only at `/kodama/secrets`. With services the workload joins the run's internal network and reaches them by service name.
- **Durable identity.** One record per workload or resource under `StateDir/kernel/NAME/`, where NAME hashes tenant, project and the engine identity (two scopes never reach each other's objects). The record, with a fresh instance UID, is written before the object exists and survives it as a tombstone. Engine objects are acted on by the bound container ID or volume instance, only after labels, UID, class, scope and specification digest are verified; a foreign object at the name is never adopted, stopped or removed.
- **Adoption and reconciliation.** `Start`/`Ensure` are idempotent on identity: an existing object with the same digest is adopted (and started if it was created but not started), a different digest is `ErrSpecMismatch`. A create is announced durably before the engine is asked. If its answer is lost, the next call looks the object up by name and UID and adopts it; if it is not observed, the request stays unresolved and **no second create is issued** (`ErrUncertain`); `Observe` reports `unknown`, a removal is never confirmed, and a late create is impossible because the identity is fenced by `Stop`. Only a command that never ran, or an engine answer that is an unambiguous refusal with nothing created, is `ErrNotReached` and safe to retry. There is no operator-retirement procedure for an unresolved create yet; it keeps its identity visible until the object is observed.
- **Fences.** Every record keeps the highest accepted fence. A `Start`/`Ensure`/`Stop`/`Remove` from an older fence is `ErrStaleFence`; a stop writes its intent first and fences the identity, so a delayed create from any fence is rejected and creates nothing; a stop of an identity nobody recorded leaves a tombstone.
- **Removal.** `Remove` stops, removes by bound ID and confirms (`PhaseAbsent`/`ResourceRemoved`) only after the engine says the object no longer exists. A running workload is reported running, not removed. A workspace is released when no container runs on it and removed (never forced) only when none references it. A backend never acts on another backend's or another scope's identity: it reports it absent.
- **Services.** Pipeline-lifetime services on a per-run `--internal` network, with the declared name as network alias. A service is `starting` until it runs and every declared port is listening (read from the container's `/proc/net/tcp*`), then `ready`; an unexpected exit is `failed` (`service_lost`).
- **Workspace preparation.** A source-free workspace is a labelled volume. A workspace with sources needs `KernelConfig.Preparer`, which supplies the one-shot container that fills it (this package never speaks Git); without one the request is refused before any effect. The preparation container has its own record, runs once, and its exit status decides `ready` or `failed` (`preparation_failed`).
- **Capabilities** (`KernelCapabilities`): `non_root`, `resource_limits`, `image_pinning`, `adopt_workload`, `fenced_stop`, `run_services`, each held by the real-engine tests. Not advertised: `network_isolation` (an internal bridge is not a filtered egress path) and `persistent_services` (project- and tenant-lifetime services, and services with secrets, are refused before any effect). Requirements the set cannot satisfy are refused with `ErrNotReached` wrapping `ErrCapability`.

`Test_unit_podman_kernel_runtime_contract` and `Test_unit_podman_adoption_and_cleanup` run against the real engine in every layer (they do not use the unit-layer service skip); with no engine they skip, with `KODAMA_REQUIRE_PODMAN=1` they fail instead. A skipped run is not evidence.
