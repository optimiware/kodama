# internal/gitops

Maintenance, retention, backup, restore and offboarding of the internal Git service (task T-138; [ADR 0011](../../docs/adr/0011-internal-tenant-git-service.md), [Git repositories](../../docs/specs/git-repositories.md) "Retention, maintenance and recovery", GR-13 to GR-15, GR-A09, GR-A10, seam S9 of the [implementation plan](../../docs/implementation/internal-git-service.md)). The operator resolution of `unknown` push entries and the restore acknowledgement it relies on live in [`internal/gitpush`](../gitpush/README.md).

**Status:** implemented and tested with real Git (temporary bare repositories), in-memory stand-ins and, for the durable state, PostgreSQL. **Not wired.** The package's durable state is migration `016_git_recovery.sql` (`internal/gitops/postgres`, `Migrations()`): backup runs and leases, the selected recovery with its completed steps and operator resolutions, and prune intents. Slot `015_git_operations.sql` belongs to `internal/gitpush/postgres` (it relaxes that module's own triggers). T-132 registers both and composes the ports; the real-worker adapter and the cross-task checks listed under "Follow-up" are not built here.

## Layout

| Symbol | Role |
| --- | --- |
| `Scheduler` | `RunOnce`/`Run`/`MaintainRepository`: per repository, serialized, prune then `Worker.Maintain`; the `maintain` assignment a worker polls calls `MaintainRepository` |
| `Scheduler.PruneRepository` | retained-pin-aware pruning of merged task, agent and run branches |
| `Pins` | `Pin`/`Release` of `refs/kodama/runs/<runId>/<n>` through the worker |
| `Backups` | `Backup` (snapshot, bundles, manifest last), `Manifest`, `Backups`, `VerifyBundle` |
| `Recovery` | `Restore`, `Reconcile`, `Discrepancies` and `ResolveDiscrepancy`: access closed until push records, refs, pins and the recovery point reconcile |
| `Offboarding` | `Offboard` stage by stage; `MayDeleteVolume` is T-129's `gitworker.Retention` |
| `PushesOf(*gitpush.Service)` | adapter to the `Pushes` port |
| `postgres` | `Store`: `BackupLeases`, `RecoveryStore` and `PruneIntents` over `016_git_recovery.sql` (forced RLS, composite keys, guards, least privilege) |
| `localgit` | **read-only** `Objects` (ancestry, commit time, bundle creation) over the Git binary, for tests and a process that mounts the volume; it never writes a repository |
| `gitopstest` | real-Git `Volume` and `Worker` (a stand-in with the T-160 semantics), in-memory stand-ins of every other port and the shared durable-state `Contract` suite |

Every collaborator is a small consumer-owned port in `ports.go`. `Worker` is the subset of `repository.Hosts` used (plus `Initialize`) with the restore fence and bundle replay of T-160 (`SetRestoreFence`, `ReplayBundle`); `Objects` (`IsAncestor`, `HasCommit`, `CommitTime`, `CreateBundle`) is the read side of the same worker contract. **No code of this package changes a repository except through the worker**: refs are created, replayed or deleted by the worker's RPCs, whose hooks, journal and mutation gate a plain `git` process would bypass.

## Maintenance and pruning

`MaintainRepository` takes the repository's lock (concurrent requests for one repository never overlap here, and the worker serializes maintenance with pushes), prunes, then calls `Worker.Maintain` with an operation ID derived from `(tenant, repository, slot)`, where the slot is `now / Options.MaintenanceInterval` (default 24 h, at least one minute). The cadence therefore needs no stored state: a repeat in the same slot (a retry, a restart, a second control-plane instance) is the identical, idempotent request; a failed call is not marked done and the next `RunOnce` retries it under the same ID; the next slot uses a new one. `RunOnce` walks tenants and repositories sequentially; a failing repository never stops the others. Archived repositories are maintained, never pruned (GR-14). **The closed-tenant check is repeated immediately before each declared deletion**, not only at the start of the pass: a restore that begins mid-pass stops the remaining deletions (the intent is released, the pass reports the tenant closed); what is left is the instant between that check and the worker's own refusal inside its restore fence. **A tenant that has an active recovery (`RecoveryStore.Current`) or closed Git access (`AccessFence.ClosedFor` for a restore or an offboarding) is skipped** by both maintenance and pruning: the report carries `Closed` (`ErrTenantClosed`, retryable, not a failure), nothing is done or marked done, and the next pass repeats it; state that cannot be read fails closed (an error). A prune between a repository's replay and the reconciliation could otherwise delete a branch the recovery point expects. The `Fence` and `Recoveries` are required configuration of the scheduler and of `Backups`.

`PruneRepository` deletes a managed branch (task, agent or run branch; never the default branch, a tag or another branch) only if **all** hold:

1. nothing references it: its name is not in `Held.Refs` and its tip is not in `Held.Commits` (the `Holds` port, implemented by the modules that own run, evidence and deployment records; an error means unknown and prunes nothing);
2. its tip is reachable from the default branch's tip or from a retained ref (`refs/kodama/runs/...`), so deleting the name loses no commit;
3. its tip commit's committer time is older than `Options.BranchRetention` (default 30 days; the age proxy that needs no stored "merged at" time).

`DeleteBranch` carries the tip as `ExpectedCommit` and an operation ID derived from `(repository, ref, tip)`: a branch that moved since it was read is kept (`ref_changed`), and a repeat after an unknown outcome is the identical request. At most `Options.MaxPrunePerRepository` (100) per pass. A deletion removes only a name whose commits another ref keeps, **but a hold can still arrive between the inspection and the deletion with the branch unchanged** (a run admitted on it, evidence naming it), which the expected value cannot see. That race is closed by the prune intent below.

### Prune intents and the hold-acquirer port (for T-147 and T-148)

`PruneIntents` is a durable reservation per `(repository, ref)` (a row with the tip and an expiry; `Options.IntentTTL`, default 5 minutes) shared by pruning and the modules that take holds. Protocol, in order:

1. **Pruning** decides a branch is a candidate, then `Declare`s the intent for its owner (`Options.Owner`; committed), **re-reads `Holds.Held`**, and deletes only if the fresh answer names neither the branch nor its tip commit; it `Release`s the intent after any definite outcome (deleted, `ref_changed`, kept). An unknown outcome (the worker call failed) keeps the intent until it expires, and the identical request is repeated by the next pass. **The per-repository lock of the scheduler is in-process only; the database intents are the cross-instance guard between pruners**: a reservation belongs to its owner, another owner's `Declare` of a ref with a live reservation is `ErrPruneBusy` (the pruner leaves the ref alone this pass, `KeptBusy`), and only the owner's `Release` drops it, so two instances pruning one repository never release each other's reservation. A restarted process has a new owner and waits for its predecessor's unreleased reservation to expire (`Options.IntentTTL`). A declaration under a project other than the repository's is an error, never a silent success.
2. **A hold acquirer** (run admission T-148, the writer reservation T-147, evidence) **commits its hold first** and then asks the `HoldGuard` port, `Conflicts(ctx, scope, repositoryID, ref, commit)`, for the branch it holds and its tip commit. On `true` it withdraws the hold and refuses the operation retryably (`unavailable`: the branch is going away); on `false` the hold stands. An error from the guard is also a refusal (fail closed).

Either the prune's re-read sees the committed hold, or the acquirer sees the declared intent; both cannot miss each other, because each side's write is committed before its read of the other's. The acquirer declares its own one-method port (`type PruneGuard interface { Conflicts(...) (bool, error) }`); `gitops.HoldGuard` is that signature, and T-132 passes `postgres.Store.Intents()`. `Holds.Held` (the same records the acquirer writes, read through T-148/T-149) must reflect a committed hold at once. The tests drive both interleavings (`Test_unit_gitops_prune_hold_race`). Retained refs are never touched by pruning or maintenance, so every pinned commit survives even the most aggressive `gc` (the real-Git test deletes the branch of a run and runs `gc --prune=now`).

`Pins.Pin` lists the repository's `refs/kodama/` refs, returns the ref already holding the commit for the run (idempotent per `(run, commit)`) or creates the next number with an operation ID from `(repository, ref, commit)`; two pins racing for a number resolve through the worker's `retained_ref_exists` and the loser takes the next. The retained refs are the record: no table. `Pins.Release` needs the `ReleaseGate` (retention) and deletes each ref with its value as expected commit; without a gate or while the gate says no it deletes nothing (`ErrRetention`).

## Backup

`Backups.Backup(tenant)` is refused (`ErrTenantClosed`, retryable) while the tenant has an active recovery or closed Git access, before anything is recorded or written, and again before it publishes if a recovery began or ended since it started (the recovery ID is compared): a backup of a half-restored volume must never become a complete backup, which could be the next restore's source. It holds the tenant's **backup lease** (`BackupLeases`, `git_backup_runs`: at most one active run per tenant, enforced by a partial unique index, so backups and the expiry that follows one never run concurrently across instances). The lease has a lifetime (`BackupOptions.LeaseTTL`, default 15 minutes) that a background renewer extends every `BackupOptions.RenewEvery` (default a third of it) for as long as the run lives, so a long bundle or upload cannot outlast it (a lost lease cancels the run at once; any other renewal error is retried at the next tick and cancels the run only when the lease is within about one period of expiring), and that is also renewed after each repository and before the manifest. Leases expire on the clock of the lease store: the PostgreSQL store uses the **database's `now()`** unless it is given a clock (`postgres.Options.Now`, for tests), so instances need no synchronized clocks; a store with an injected clock needs instances that agree to within a small fraction of the TTL; an expired active run is **abandoned** (recorded failed) by the next `Acquire`, and its owner, resuming, finds `ErrLeaseLost` at the next renewal or at `Complete` and publishes nothing (its manifest, if written, is withdrawn with its bundles). Then: take the volume snapshot **first**, then, per repository, stream a bundle of every ref (heads, tags, retained refs) to object storage while hashing it (`Objects.CreateBundle`; a repository without refs has no bundle and is marked `empty`), and write `git-backups/<tenant>/<backupId>/manifest.json` **last** (snapshot ID and time; per repository the key, size, SHA-256, journal head and the exact refs), then `Complete` the run. If `Complete` returns an error other than `ErrLeaseLost` its outcome is unknown: the run's state is read again before anything is deleted, a run recorded complete is returned as published, a run recorded active is cleaned up and failed, and when the state cannot be read the objects are kept (the lease then lapses and the run is abandoned and expired like any failed one). A bundle the worker reports `consistent=false` (a receive or server operation ran while it was captured, so refs and journal head are not one boundary) is retaken up to three times; a repository that never settles fails the backup. A backup counts only when its run is recorded **complete** (`Backups`, `Manifest` consult the run table); any failure removes what was written and leaves earlier backups alone.

**Expiry** runs after the run completed and **without its lease**, so a recovery can begin while it runs. It computes the protected set (the backup an active recovery selected) when it lists the store and **reads the guard again before it deletes each complete backup**: an active recovery's source is skipped, and a closed restore fence (a restore that has not yet recorded its source: `Restore` reads the manifest first) or an unreadable state defers every remaining complete backup to the next backup's expiry (fail closed; the objects of failed runs, which no recovery can read, are still removed). It removes only (a) complete backups beyond `BackupOptions.Keep`, oldest first, manifest first, except the backup an active recovery reads, and (b) the objects of runs recorded **failed**. It never removes an upload merely because a newer manifest exists, a run whose lease is live, or objects without a run row. Every key starts with the tenant; a manifest naming another tenant, another backup or a bundle key outside its backup is `ErrBackupCorrupt`.

## Restore

```text
Restore:    Fence.Close(restore)  -- fails: nothing touched
            RecoveryStore.Begin   -- the source is durable before any step (a different source while one is active: ErrRecoveryActive)
            -> Snapshots.RestoreVolume(snapshot)            (optional; recorded)
            -> per manifest repository (every one, empty ones too):
                 Worker.Initialize
                 non-empty: digest verified -> Worker.SetRestoreFence(true) -> Worker.ReplayBundle (creates MISSING refs only) -> SetRestoreFence(false)
                 RecoveryStore.MarkReplayed                 (recorded only after the fence was left)
            -> Reconcile
Reconcile:  only while a recovery is active and access is closed for it (ErrNotRestoring otherwise), per repository:
            the replay completed -> gitpush.Reconcile -> Settlement -> worker journal head -> pins -> the recovery point -> AcknowledgeRestore
            every step complete and every repository consistent -> RecoveryStore.Complete -> Fence.Open(restore)
```

**Durable, resumable.** The selected source (snapshot and the concrete backup ID; `latest` is resolved once and a resumed `Restore` keeps it), the volume restore, each repository's completed replay (with its result) and each operator resolution are stored (`RecoveryStore`, `git_recoveries`, `git_recovery_replays`, `git_recovery_resolutions`) before access can reopen. A failed replay, a restart or another instance never reopens a half-restored volume: `Reconcile` reads the store and keeps a repository whose replay is not recorded closed (`the bundle replay of backup … has not completed`). `Restore` with the same source resumes and repeats only the steps that did not complete; the replay operation ID is derived from `(tenant, recovery, repository)`, so a repeated replay is the identical, idempotent worker request. A crash between completing the recovery and opening the fence is finished by the next `Reconcile`.

**Worker semantics (T-160).** The replay never writes a ref itself: the worker creates only refs the repository **lacks**, never advances, rewinds or deletes one, and reports each ref that exists at another value with its relation (`repository_ahead`, `bundle_ahead`, `diverged`). It accepts the replay only while the repository is fenced for restore. The worker fence is left right after the replay (not at the end of the reconciliation) because the reconciliation recreates retained refs, a server ref operation that a fenced repository refuses; the tenant's access fence (`AccessFence`) stays closed throughout, and a fence that cannot be left means the replay is not recorded and the next pass repeats it.

**Unlisted repositories.** A repository of the backup that the `Catalog` no longer lists (deleted since the backup) is not initialized, replayed or reconciled: it would be recreated on the worker and never verified. It is skipped and reported in `Report.Unlisted`, and does not block the recovery.

**Reconcile against the recovery point.** For every repository of the backup the volume must equal the manifest's refs: a missing ref (the replay did not or could not create it), an **extra** one (a branch deleted before the bundle that an older snapshot brings back) and a **differing** one (the volume is older, newer or rewritten; the replay does not move it) is each a `Discrepancy` that keeps access closed until an audited operator resolution (`Discrepancies` lists them, `ResolveDiscrepancy` accepts one). A resolution names the discrepancy exactly as listed, including the observed commit, so one that no longer holds is `ErrNotDiscrepancy` and a ref that changes again needs a new resolution; it is stored with its audit row in one transaction (`git.recovery.discrepancy_resolved`) and never changes a ref. Retained refs (`Held.Pins`) are reconciled against the run records instead of the manifest.

**Other blockers:** push entries still in flight, a damaged journal (the definite `journal_unreadable` answer; any other worker failure also blocks), a retained ref the run records expect that is at another commit or whose commit the restored repository lacks (`LostPins`), and any failure to read a dependency. A missing pin whose commit exists is recreated (`PinsRepaired`). **Not blockers:** `unknown` entries, which stay visible and keep blocking their writers and new seeds until an operator resolves them (`gitpush.Service.ResolveUnknown`). A volume restored from an older snapshot (journal head below the one the control plane saw) makes gitpush settle the in-flight entries `unknown` (`journal_regressed`), never refused and never applied; once nothing is in flight the restored head becomes the baseline (`AcknowledgeRestore`, audited). The `AccessFence` is the repository-level "restoring" fence the Git endpoint (T-132) consumes: while closed for `restore`, smart HTTP, credential issuance and push authorization answer a retryable 503.

## Offboarding

`Offboard(tenant)` is idempotent and repeated until `StageDeleted`: the lifecycle must say the tenant is offboarded (`ErrNotOffboarding`); Git access is closed (`FenceOffboarding`); every grant is revoked (`Grants.RevokeAll`) and counted; every repository's pushes are reconciled and none may be in flight (`StageSettling`); retention must have elapsed with no hold (`StageRetaining`); the deletion is recorded in the audit trail first (a failing audit deletes nothing); then `StorageOffboarder.OffboardTenant` (T-129) deletes the volume, which consults `Offboarding.MayDeleteVolume` again. **Decision:** `unknown` entries do not delay deletion (the data is being deleted; retention is the window for an operator); they are counted in the result and the audit event. Run cleanup and pipeline completion never reach this path.

## Follow-up for other tasks (not built here)

- **T-160 / T-132: the worker adapter.** `Worker.SetRestoreFence`/`ReplayBundle` and `Objects` are the control-plane side of T-160's worker operations (`contracts/git/v1/objects.go`: `IsAncestor`, `HasCommit`, `CommitTime`, `CreateBundle` under the shared gate with `consistent`, `ReplayBundle` only inside the restore fence, `SetRestoreFence`). `gitopstest.Worker` and `localgit` implement the same semantics with plain Git for tests; **the real-hooks test against a repository initialized by `internal/gitservice` (replay through the worker's hooks, journal entries of the replay, `restore_fence_required`, a pin repaired after the fence) belongs to the T-160/T-132 integration**, not to this package. The adapter maps `repository_ahead`/`bundle_ahead`/`diverged` conflicts to `ReplayResult.Conflicts` with the `Relation`, `consistent=false` to `Bundle.Consistent=false`, `repository_empty` to `ErrEmptyRepository` and the JSON-frame body to the `io.Reader`/`io.Writer` of the ports.
- **T-132:** registers `postgres.Migrations()` at slot `016` (after `015`, `gitpush/postgres.OperationsMigrations()`), builds `postgres.NewStore(pool, postgres.Options{})` (database clock) and passes `Leases()`, `Recoveries()` and `Intents()`, with the same `AccessFence` and `RecoveryStore` to `Backups` and `Scheduler`; adapts `Catalog` (internal, provisioned repositories per tenant, `archived` flag), `Holds` over run/evidence records (`Held.Commits`, `Held.Refs`, `Held.Pins`), `ReleaseGate`, `BackupStore` over the artifact S3 adapter plus a `List` operation, `Snapshots` over the storage class's snapshot capability, `Lifecycle`, `Auditor` and `AccessFence` (a durable per-tenant closure consumed by the Git endpoint and the credential and push-authorization routes); exposes `Recovery.Discrepancies`/`ResolveDiscrepancy` on the operator surface with its own authorization (the actor is recorded); calls `Scheduler.Run`, `Recovery` and `Offboarding` from the operator/lifecycle surface.
- **T-147 and T-148 (hold acquirers):** after committing a hold on a branch or commit of an internal repository, call the `HoldGuard` port (`Conflicts`, above) and withdraw and refuse retryably when it answers true; `Holds.Held` must show a committed hold at once.
- **T-132 (Grants adapter over T-161):** `gitauth.Service.RevokeAll(ctx, tenant, reason, actor) (int, error)` and `Active(ctx, tenant) (int, error)` exist; the adapter calls `RevokeAll` with the reason "tenant offboarding" and the offboarding's system actor, discards the count and passes `Active` through; `Offboard` repeats until `Active` is zero, after closing the access fence (issuance is fenced first).
- **T-129:** pass `Offboarding` as `gitworker.Config.Retention`.
- **docs/implementation/internal-git-service.md** still reserves migration `015` for T-138 only; the numbering is `015` gitpush (operator actions) and `016` gitops (recovery state).
