# `internal/gitservice`: the tenant Git worker

The package behind `kodama git serve` ([ADR 0011](../../docs/adr/0011-internal-tenant-git-service.md), [Git repositories](../../docs/specs/git-repositories.md), [T-128](../../docs/tasks/T-128-git-worker.md)). It wraps native Git: `git http-backend`, `receive-pack`, `upload-pack`, hooks and `git maintenance`. Wire shapes and error codes are the [Git service contract](../../contracts/git/README.md) (`gitv1`); nothing here redefines them. **Nothing is registered in the binary yet**: `kodama git serve` and `kodama git-hook` are wired by T-132.

## Entry points for T-132

| Symbol | Use |
| --- | --- |
| `ServeCommand(Config)`, `(*Command).Run/Serve` | `kodama git serve`: validates the configuration, serves Git, the RPC and `/healthz` on one listener, polls assignments, shuts down gracefully |
| `HookMain(args, stdin, stdout, stderr, environ)` | `kodama git-hook <name> [args...]`: the process the hook shims run; returns the exit status |
| `NewControlPlaneClient(baseURL, tenant, TokenSource, *http.Client)` | the `ControlPlane` port over HTTPS to `gitv1.ControlBasePath` with the worker identity |
| `Service.GitHandler()`, `RPCHandler()`, `Handler()` | smart-HTTP endpoints, the `repository.Hosts` RPC under `gitv1.WorkerBasePath`, or both plus `/healthz` |
| `AssertionVerifier`, `ControlCallerVerifier` | injected by T-136: signature verification of forwarding assertions and of the control plane's calls (a missing verifier is a configuration error: default deny) |

## Smart HTTP

Only `GET /<repositoryId>.git/info/refs?service=git-upload-pack|git-receive-pack` and `POST /<repositoryId>.git/git-upload-pack|git-receive-pack` are served; every other path or method is 404. The control plane sends the forwarding assertion in the `Kodama-Forwarding-Assertion` header (`AssertionHeader`). The worker verifies it through `AssertionVerifier`, then applies `gitv1.CheckForwarding` (tenant, audience, lifetime), `CheckService` (`receivePack`) and requires the assertion's repository to equal the path's; the on-disk path is `<DataRoot>/repositories/<repositoryId>.git`, built from the validated opaque ID only. `Git-Protocol` (protocol v2) is passed through after a syntax check.

Request bodies are spooled to an unlinked temporary file under `<DataRoot>/spool` within `Limits` (a gzip body is inflated while spooling, so the limit bounds the decompressed size): Git sends a push larger than `http.postBuffer` chunked, which `net/http/cgi` rejects. Concurrency, duration and slow-body time are bounded and refused explicitly (413, 429 with `Retry-After`, 503 during maintenance). A receive runs to its own end once its pack is on disk, whatever the client does, in its own process group.

## Configuration that cannot be replaced

Every Git process starts from an empty environment (no inherited `GIT_*`, `HOME` or credential) plus `GIT_CONFIG_NOSYSTEM=1`, a worker-owned `GIT_CONFIG_GLOBAL` file and the same settings as command-scope configuration (`GIT_CONFIG_COUNT`), which Git ranks above a repository's own config file. That is what makes `core.hooksPath`, `uploadpack.allowAnySHA1InWant` and friends, `receive.fsckObjects`, `receive.maxInputSize`, `receive.hideRefs` and `uploadpack.hideRefs=refs/kodama` unreplaceable by anything in the repository. Initialization also writes the provisioning settings into the repository's config.

## Hooks, journal and the fence

```text
git http-backend -> receive-pack -> pre-receive / reference-transaction / post-receive
                                     \_ kodama git-hook <name>  -- loopback HTTP, per-receive token -->  worker -> ControlPlane
```

- `pre-receive` reads the updates, computes `gitFacts` (`repositoryEmpty`, `fastForward`), calls `Authorize` and prints denials to the client. A refusal fails the whole receive.
- `reference-transaction` `prepared` (refs locked) reads each ref's value with `for-each-ref` (exact match), **appends** the receive-attributed `prepared` entries with `observed` to the journal (one write, `fsync`), and only then requests commit intent. Any failure exits non-zero and Git aborts; the `aborted` state appends `aborted` for the transaction's own pending `prepared` entries. Git also runs the `committed` state for refs it rejected inside a non-atomic receive (a directory/file ref conflict, for example), and other receives run concurrently on the same refs (receives hold the gate shared and Git releases its ref locks before that hook), so neither Git's report nor a ref value read at some moment proves what this transaction did. That hook therefore decides **under the journal's exclusive append lock**, the lock every `prepared` entry is appended under while its ref lock is held. For each update it locates the transaction's own pending `prepared` entry; if any later `prepared` entry exists for that ref (of any receive or operation) it appends nothing and the settlement decides from that entry's `observed` value; otherwise no other transaction can have changed the ref (one that holds its ref lock cannot journal `prepared`, and so cannot commit, until the lock is released), so it reads the ref's exact value with `for-each-ref` and appends `committed` (the ref holds the new value, absent for a delete), `aborted` (it holds the old value, absent for a create), or nothing (any other value, or a value that cannot be read). `post-receive` lists only the refs Git applied, so the journal and the report agree.
- `post-receive` reports the applied refs; the worker retries a failed report in the background with the same body. It then prints one line to stderr, which Git relays to the pusher as `remote: kodama-push-id: <pushId>` (`PushIDLinePrefix`).
- A Git process the worker did not start has no hook environment, so the hooks refuse any ref change.

The journal is `<repository>/kodama/journal.jsonl`: JSON lines in the `gitv1.JournalEntry` shape, appended under an exclusive `flock`, sequence from 1 without gaps; a torn final line is truncated by the next append and ignored by readers; any other damage fails closed. The journal-read RPC answers a journal it affirmatively found corrupt, undecodable, with a sequence gap or **missing from an initialized repository** with the definite `409 journal_unreadable` (`gitv1.CodeJournalUnreadable`); the control plane maps exactly this code, and nothing else, to `gitpush.ErrJournalUnreadable` and settles the affected entries `unknown`. A read that failed for a reason unrelated to the journal's content (an I/O error, a path that is not a file) is the transient `503 unavailable`: nothing is concluded and the reconciler retries. The server-side operations and `ReadRefValues` keep reporting an unreadable journal as `503 unavailable`.

## Client-visible behavior

Git does not return the push record to the pusher, so the worker does. For every receive that applied at least one update, `post-receive` prints exactly one line `kodama-push-id: <pushId>` to stderr (`git push` shows it as `remote: kodama-push-id: <pushId>`, also with `--porcelain`), where `<pushId>` is the `pushId` of the control plane's authorization response for that receive. The workload entrypoint parses it. Rules:

- It is printed after the outcome was sent, and also when the outcome call failed or was refused (the record exists; the control plane reconciles).
- It is never printed for a receive that applied nothing (an up-to-date push starts no receive; a denied receive or one whose commit intent was refused never reaches `post-receive`), and never more than once per receive (the worker hands the ID to the hook once). A multi-ref push, atomic or not, is one receive and shows one line.
- It carries nothing but the push ID: no token, grant or credential.
- It is the only line that starts with `kodama-push-id: `. Every other hook diagnostic is one physical line prefixed `kodama: `; text that comes from outside the hook (control-plane messages, ref names, Git or filesystem errors) has control characters, line and paragraph separators and invalid UTF-8 escaped, is bounded to about 1000 bytes, and has the marker text inside it defused (`kodama-push-id\:`), so no message can forge a push ID line. The ID itself is printed only if it has the opaque-ID syntax.
- Other client-visible lines are unchanged: denials print `kodama: refused <ref>: <reason>` and `kodama: push refused: …` before the push fails.

## Mutation gate and termination

One gate per repository: receives and server-side ref operations (`CreateBranch`, `DeleteBranch`, retained refs, which run `git update-ref` through the same hooks and are journaled under their `operationId`) hold it shared; maintenance holds it exclusively and is never starved (bundle creation holds it shared as an observer; the restore replay and the restore-fence entry hold it exclusively, see below). `ReadRefValues` reads under the gate's mutex and reports `Quiescent` only when nothing was in progress. At the deadline from the authorization response (and at `Limits.MaxDuration`, or when an RPC's deadline passes) the whole process group is killed. The worker then waits for the group to be **verified gone** (the leader reaped and `kill(-pgid, 0)` reporting no member) before it repairs the repository. Until then the repository is fenced: `ReadRefValues` is not `Quiescent`, a killed receive still reports `running`, and receives, ref operations, maintenance and the repair itself are refused with `503 unavailable`; a ref lock of a repository with a live group is never deleted. The fence is rechecked wherever a request could have queued before it was raised: on every iteration of the exclusive admission, after the operation mutex is taken and before refs are observed, settled or changed. Initialization and reconfiguration (`config` writes, `symbolic-ref HEAD`) run under the same gate (shared, so they never overlap the repair, which could otherwise delete a live `HEAD.lock`) and are refused while fenced. Every command that changes a repository, with hooks or without, has its process group tracked and verified gone; read-only commands are not. Once the group is gone and the repository idle, the killed transaction's ref locks, the `packed-refs` lock and the incoming-object quarantine are removed. The `prepared` journal entries stay for settlement.

## Outcomes for `repository.Hosts` (T-127's adapter)

No wire extension: the adapter uses the classification in [the contract](../../contracts/git/README.md#consumer-owned-ports) (`Refused`, `Unavailable`, `Unknown`).

| Worker answer | `Outcome` |
| --- | --- |
| `200` | success |
| a contract error body whose code has that code's `gitv1.Status` (for example `409 branch_exists`, `409 journal_unreadable`, `404 not_found`, `400 invalid_request`) | `Refused` with the `ContractError`: nothing changed |
| `503 unavailable` (also `429`, an unreachable or not-ready worker, a fenced repository, a worker that refused to start) | `Unavailable`: the request did not change anything; retry with backoff |
| a transport failure after the request was sent: the connection closed without a response, a reset or a timeout, an unreadable response | `Unknown`: repeat the identical request |

The worker produces the last form on purpose for a mutation that may have been applied: `update-ref` killed or cancelled after it started (for example while the `committed` hook runs after the ref was published), an initialization that failed after the repository was published or while its configuration was being reapplied, and a maintenance that failed or was cancelled after it was launched. It aborts the HTTP response (`panic(http.ErrAbortHandler)`), so the caller sees no status at all. A contract error body therefore always means a definite refusal or that nothing changed. Retrying is safe: `CreateBranch`/`SetRetainedRef` find the ref at the commit (success, `created: false`, the open journal transaction closed as committed) or absent (the open one closed as aborted, then redone); `DeleteBranch`/`DeleteRetainedRef` find it absent (`deleted: false`); `Initialize` is idempotent on the path; maintenance simply runs again. A branch that now points to another commit is `branch_exists` for every request naming a different commit, including the retry of the operation that created it.

## Object operations, bundles and the restore fence (T-160)

Six more RPCs under `gitv1.WorkerBasePath` give T-138's `internal/gitops` the object-level operations of maintenance and recovery without mounting the tenant volume (`Objects` and the restore half of `Recovery`). DTOs, schema and fixtures are `contracts/git/v1/objects.go`; the new codes are `commit_not_found` (404), `repository_empty` (409), `bundle_too_large` (422) and `restore_fence_required` (409).

| Route (under `/repositories/{id}`) | Operation |
| --- | --- |
| `POST /objects/is-ancestor`, `/objects/has-commit`, `/objects/commit-time` | read-only; no gate, no hooks; `commit_not_found` for a commit the repository lacks (a tree, a blob or an annotated tag object is not a commit); `HasCommit` answers `false` instead |
| `POST /files` | read-only; `.kodama/*.yaml` and `.yml` at one exact commit (a path, or the directory `.kodama/` for its direct files): at most 64 files, 256 KiB each, 1 MiB together, refused whole beyond that; a missing file is absent, a missing commit is `commit_not_found`; sanitized environment, no hooks, replacement objects ignored (T-168) |
| `POST /bundles/create` | the answer is `gitv1.BundleMediaType`: one JSON line (the manifest) then the bundle bytes |
| `POST /bundles/replay` | the request is `gitv1.BundleMediaType`: one JSON line (`ReplayBundleRequest`) then the bundle bytes |
| `POST /restore-fence` | enter or leave the restore fence |

Every object read runs Git with the sanitized environment, no hooks and `GIT_NO_REPLACE_OBJECTS=1`: a client can push `refs/replace/*`, and a replacement must never change an ancestry or commit-time answer. `CommitTime` is the committer time in whole seconds UTC; a timestamp outside years 1 to 9999 is clamped (a far-future commit stays "not old" for age-based pruning).

**`CreateBundle`** takes the repository's gate **shared, as an observer**: it excludes maintenance, the replay and the fence entry, never a receive or a server ref operation. Registering as an observer excludes maintenance and the replay; one snapshot under the gate's mutex (no I/O there) records whether any receive or operation was running and the admission epoch, and then the journal head and the refs are read **outside** the mutex (only the prefixes `refs/heads/`, `refs/tags/` and `refs/kodama/` are scanned; with `refs: null`, all of them; `repository_empty` when there are none, `bundle_too_large` above `gitv1.MaxBundleRefs`; an explicit ref that does not exist is `not_found`, one outside those namespaces `invalid_request`). This is sound because a mutation either was running at the snapshot (not quiescent) or is admitted later and bumps the epoch, which the end-of-bundle check compares. A ref inside those namespaces whose name the contract's ref syntax cannot express makes the bundle a definite `400 invalid_request` naming the ref: a backup never silently loses a ref (name the other refs explicitly to bundle around it). Then it runs `git bundle create --stdin` into a per-request directory under `<DataRoot>/tmp`. The manifest's `refs` are read back from the bundle file with `git bundle list-heads`, so they are exactly what it holds, and its `journalHead` is the head read before the refs were captured. `consistent` is about concurrent mutation, not recovery state: a bundle taken while the **restore fence is raised** is still reported consistent (nothing mutates then). It is true only when no receive or operation was running when the capture was made, none was admitted until the bundle was complete, no killed Git process fenced the repository, and the bundle holds exactly the captured refs; otherwise the control plane must not treat `refs` and `journalHead` as one boundary. The size is bounded by `Limits.MaxBundleBytes` (a watcher stops Git when the file passes it, `bundle_too_large`, nothing is left behind) and the time by `Limits.BundleTimeout`; `Limits.MaxConcurrentBundles` (default 2) bounds the bundle creations and replays at once (`429 rate_limited` with `Retry-After`). The gate is released **before** the bytes are streamed, so a slow reader never holds maintenance off; `Content-Length` is exact and a failed copy aborts the response.

**The restore fence** (`SetRestoreFence`) is a per-repository state, entered by the control plane before it restores a repository and left when the repository is reconciled. While it is raised, receives, server ref operations (`CreateBranch`, `DeleteBranch`, retained refs) and maintenance are refused with `503 unavailable`; initialization, reconfiguration, reads, upload-pack and `CreateBundle` are admitted; `ReplayBundle` is admitted and is refused (`409 restore_fence_required`) at any other time. Entering takes the gate exclusively, so it **waits for running receives and operations**, and anything that queued behind it is refused once it is raised; leaving waits for a running replay. A leave that has nothing to do (the flag is clear and no marker exists) answers without taking the gate, so it never stalls receives. Both directions are idempotent (`changed` says whether the state moved) and may be requested for a repository that does not exist yet (a restore raises the fence, initializes the repository, then replays). The fence is **durable**: a marker file `<DataRoot>/restore-fences/<repositoryId>` is written and synced before the flag is set, and removed before it is cleared, under the exclusive gate, so a failure to persist leaves the fence as it was. A replacement worker reads the markers after it holds the generation lock and before it serves anything, so it comes up **closed** for every repository whose fence was raised. Loading **fails closed**: a marker directory that cannot be read makes `New` fail (the worker cannot know what is fenced, so it serves nothing), and any entry named like a repository ID is a fence whatever its file type; a leave removes it. The markers live on the volume: a volume restored from a snapshot brings the markers of the snapshot with it, so the control plane (whose access closure is durable) raises the fence again after restoring a volume, whatever the marker says.

**`ReplayBundle`** first refuses outside the fence (before reading the bundle), then spools the body to a per-request file bounded by `Limits.MaxBundleBytes` while hashing it, verifies `sha256` when given (`invalid_request`, nothing touched), and only then takes the gate exclusively and rechecks the fence. The replay runs to its own end whatever the client does. It then:

1. reads the bundle's refs; a body that is not a bundle, a bundle without refs, or one naming a ref outside `refs/heads/`, `refs/tags/` and `refs/kodama/` is `invalid_request`;
2. stores the objects with `git index-pack --stdin --fix-thin --strict` over the pack that follows the bundle header (the object checks of a receive; `git bundle unbundle` does not apply them), after checking that every prerequisite commit exists; this updates no ref. A missing prerequisite, a damaged pack or an object strict checking rejects is `invalid_request`. It then verifies with `rev-list --objects` that every tip it will create or compare is complete down to the roots;
   and refuses, still before any ref exists and with a definite `invalid_request`, what Git would refuse on every attempt: a head or hidden ref whose tip is not a commit, and a ref that collides with another as a directory and a file (`refs/heads/a/b` against an existing `refs/heads/a`, or the reverse; the message names both). The operator removes the colliding ref, or restores into a fresh repository, and repeats the replay;
3. creates each **missing** ref through the worker's own ref path (`git update-ref` with the hooks, attributed to the request's `operationId`), so a real repository with `core.hooksPath` accepts it and the journal records `prepared`/`committed` for exactly the refs it created;
4. leaves every other ref alone: a ref at the bundle's commit is `unchanged` (an earlier attempt's open journal entry is closed committed); a ref at another commit is `conflicting` with `repository_ahead` (the bundle's commit is an ancestor of the repository's), `bundle_ahead` or `diverged`, and is neither advanced nor rewound; a ref the bundle does not name is never deleted.

Everything before step 3 is a definite refusal (objects stored by step 2 are unreferenced and harmless). From the first ref creation on, any remaining failure (a lock another process holds, a failed hook, a journal write) is an **unknown outcome**: the response is aborted like every other possibly-applied mutation and the caller repeats the identical request, which finds the created refs `unchanged`, settles an interrupted journal entry and creates the rest. A repeat of an applied replay reports the refs it created as unchanged and journals nothing; a different `operationId` over the same state behaves the same.

## Generation fence and crash recovery

The worker takes an exclusive `flock` on `<DataRoot>/worker.lock` before it touches anything, and passes that descriptor, **without close-on-exec** (`cmd.ExtraFiles`, so it is descriptor 3 in the child), to every Git process it starts: `http-backend` and the `receive-pack`/`upload-pack` it runs, `update-ref`, `symbolic-ref` and `config` during initialization, `for-each-ref` and maintenance. The hooks and every other descendant inherit it, so the lock is released only when the last process of the generation has exited. **The Kodama hook binary must keep descriptor 3 open** (it does nothing with it; do not close inherited descriptors or set close-on-exec on it), and anything that execs Git on the worker's behalf must preserve it. The Go hook does so explicitly: it receives the lock as descriptor 3 and passes it as `ExtraFiles[0]` to the Git processes it starts, because `os/exec` would otherwise drop it. Any other trusted descendant that starts processes must do the same.

A replacement worker therefore cannot start while any process of a previous generation lives: `New` waits up to `Limits.LockWait` (default 30 s) and then fails with `ErrDataRootBusy`, having touched nothing (`kodama git serve` should report not ready and exit so the Service keeps the old state). Only once it holds the lock, and before any handler is served, it removes ref and `packed-refs` locks and incoming-object quarantines from every repository: provably abandoned. Refs and the journal are never modified: the `prepared` entries of interrupted transactions stay for settlement. No process records or timing heuristics are involved.

## Known limits

- Git `die`s when a `prepared` hook refuses, so a refused commit intent ends the receive without a message to the client (the reason is logged by the worker); depending on the Git version the refs of one receive are one batched transaction or one per ref, and the journal records whichever Git did.
- Protocol v2 lets a client want any object whose ID it knows, so `refs/kodama/*` is hidden by name, not by content; confidentiality granularity is the repository (ADR 0011).
- An outcome entry finds its transaction's prepared entry by scanning the journal backward from the end in 256 KiB blocks until every tuple is resolved: no cutoff, and one block in the usual case. A tuple that never appeared (an abort whose prepared entry was never written, a first attempt of an operation) reads the whole journal.
- Locks are removed only at startup (after the generation lock is held) and after a receive, RPC Git or maintenance the worker killed whose process group is verified gone. A process that leaves its group (for example by `setsid`) is not found by the runtime check; the generation lock still covers it at the next start.
- A bundle is spooled to `<DataRoot>/tmp` (creation) or a per-request file there (replay): the volume needs room for the largest bundle, bounded by `Limits.MaxBundleBytes` (default 8 GiB).
- `ReplayBundle` never recreates a deleted ref over a divergent value and has no "force": a repository that must be rolled back to a bundle is restored from the volume snapshot first, then replayed.
- The object-operation tests are `Test_unit_gitservice_is_ancestor`, `..._has_commit_and_time`, `..._bundle_create_under_shared_gate`, `..._bundle_replay_only_while_fenced`, `..._restore_fence_races` and `..._replay_never_rewinds`.
- Linux and macOS only (process groups, `flock`).
- The tests build `internal/hookmain` as the hook binary (a stand-in for `kodama git-hook`).

## Receive recovery and its bounds (reconcile.go)

The control plane keeps no push-record table; the journal is the evidence and the worker re-reports it (`Service.Reconcile`, on the `reconcile` assignment, whose `journalAck` is the control plane's acknowledged sequence). A receive ID carries its grant, so the journal alone attributes a receive.

- **Pages.** One pass reads at most `sweepEntries` (default 65,536) journal entries after its cursor, the larger of the acknowledged sequence and the sequence the worker itself settled. The receives that begin in that page are the candidates. A backlog larger than a page is swept page by page: each pass settles its page's receives, acknowledges up to the page's last sequence and the next pass continues after it. A page holding only server operations has nothing to report, so the cursor alone moves past it.
- **Complete evidence.** Liveness is established first, then the complete journal evidence of the ended candidates is read in one snapshot bounded by `snapshotEntries` (default 1,048,576). A receive that was still running is never reported, and neither is one whose evidence exceeds the bound (the pass fails explicitly and settles nothing).
- **Attribution.** A committed entry is applied, an aborted one is not. An entry with only its prepared record is decided by the ref's next value: the observed value of the next prepared entry of that ref, by any receive or operation, or else the ref's current value with an absent ref read as the all-zero ID and the journal unchanged around the read. Equal to the new value is applied, equal to the value before is not, anything else is ambiguous. A receive with one ambiguous update is not reported and nothing after it is acknowledged; it stays unacknowledged until later evidence decides it.
- A live outcome carries `journalSequence` only when every other receive in the window after the acknowledged sequence is reported or has applied nothing.
