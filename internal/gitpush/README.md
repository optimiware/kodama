# internal/gitpush

Push authorization, the push journal and the `git.refs_updated` event of the internal Git service (task T-130; [ADR 0011](../../docs/adr/0011-internal-tenant-git-service.md), [Git repositories](../../docs/specs/git-repositories.md) GR-07, GR-09 to GR-11, GR-18, GR-19, GR-A04 to GR-A06 and GR-A13 to GR-A15, seams S4 and S8 of the [implementation plan](../../docs/implementation/internal-git-service.md)). The wire shapes, reasons, settlement decision and event are the executable contract in [`contracts/git/v1`](../../contracts/git/README.md) and [`contracts/events/v1`](../../contracts/events/v1); this package applies them and redefines none.

**Status:** implemented and tested on the memory adapter; the PostgreSQL adapter is written and its tests need the services stack. **Not wired.** No route is mounted, no migration is registered and no adapter to the peer modules exists: T-132 lists migration `009_git_pushes.sql` (after `007` and `008`), mounts the routes and adapts the ports below. The published API document does not include `api/git-pushes.yaml` until T-158 lists it.

## Authorization

`Authorize` reads, outside any SQL lock, the repository (`Repositories`), the grant's **effective** claims (`Grants.Claims`, which re-checks the person's roles, attempt liveness, expiry and revocation: a demoted engineer's unexpired credential records no update right, a cancelled attempt's is `invalid_credential`) and, for a workload's task-branch updates, the writer reservation (`Reservations`). `Evaluate` then decides every update; a receive with any deny fails as a whole and is recorded settled (`refused`: the denied entries with their reason, the others `no_commit_intent`), so it cannot hold a seed open and a replay returns the same verdicts. Order of rules: archived repository (`repository_archived`), attempt no longer live (`attempt_inactive`), the seed rules, server-only and unclassified refs (`ref_protected`), then the grant kind and ref class:

| Ref class | human (current engineer) | attempt | integration | seed |
| --- | --- | --- | --- | --- |
| default branch | fast-forward only, only with `directPushToDefault`; never create or delete (`ref_protected`, `not_fast_forward`) | never (`ref_protected`) | exactly the constrained update as a fast-forward (`integration_mismatch`, `not_fast_forward`) | the one create of an empty repository |
| task branch | anything; a non-fast-forward is a `rewrite`, audited | create or fast-forward by the reserved writer; rewrite `not_fast_forward`; delete or no reservation `ref_protected` | `integration_mismatch` | `seed_only` |
| agent and run branches | anything | any attempt of the named run, whatever its declared access | `integration_mismatch` | `seed_only` |
| other branches | anything | only a pattern the grant names (`grant_scope`) | `integration_mismatch` | `seed_only` |
| tags | anything | creation only, by a grant naming the pattern (`ref_protected`) | `integration_mismatch` | `seed_only` |

A viewer's or demoted person's grant has an empty update set (`grant_scope`); a preparation grant updates nothing. **The repository facts are fenced.** The policy is evaluated under a snapshot read before the transaction; inside the authorization transaction the repository's row is re-read and held (`Tx.RepositoryState`: `SELECT … FOR SHARE` on `repositories` under RLS with the runtime role's grants from `007`, which include the column `UPDATE` that `FOR SHARE` needs) and compared with the snapshot (hosting, status, default branch, direct-push policy; the version is ignored because emptiness reports bump it). An archive, a new default branch or a disabled policy that lands in between refuses the receive as retryable (`unavailable`), creates no record, and the worker's retry evaluates fresh facts. A foreign or unknown repository or grant is `not_found`; a grant never spans another project's repository; an external repository is `hosting_mismatch` and a provisioning one `repository_not_ready` (errors, not verdicts). The bound of updates per receive (`Options.MaxUpdates`, the contract ceiling 1024) is `too_many_updates`.

**The writer reservation is rechecked after the record commits.** The reservation read before the transaction (the fast path that lets `Evaluate` deny at once) can be released, or the workspace archived, between that read and the commit of the `authorized` record, and the workspace's `UnsettledOnRef` cannot see an uncommitted row. So, for an attempt's allowed task-branch updates, `Authorize` calls `HoldsWriter` again after the record (and the seed consumption) is durably committed and **before the verdicts are returned**. A work item whose reservation was lost settles the record refused in its own transaction (`Record.RefuseLostWriter`: the task-branch entry `ref_protected`, every other still-authorized entry `no_commit_intent` since the receive fails as a whole; audit `git.push.authorized` then `git.push.refused` with the reason; no event) and the worker is told the denial, which a replay of the receive repeats. A reservation that cannot be read at that point is a retryable outage that decides nothing (the record stays authorized; its replay is the stored allow). `CommitIntent` therefore also reads the reservation, outside any SQL lock like the liveness, for the task-branch entries it newly moves to committing, and refuses with `forbidden` (`ref_protected`) when it was lost; a repeat for entries that already hold intent is not rechecked. A person's push never reads the reservation.

**Seed.** The one allowed seed receive creates exactly `refs/heads/<defaultBranch>` while the worker reports the repository empty; any other update, alone or beside it, refuses the whole receive as `seed_only` without consuming the grant. Inside the authorization transaction `consumeSeed` takes the repository's seed lock (`GrantTx.LockSeed`), refuses (`seed_consumed`) when any other push record of the repository is unsettled and then calls `gitauth.ConsumeSeedIn` **before** the record is inserted, so concurrent seed receives authorize at most one, a replay of the consuming receive is idempotent, and `UnsettledPush` (which implements `gitauth.Pushes`) keeps a new seed grant from being issued while the first receive is authorized or unknown.

## Settlement

```text
authorized --commit intent--> committing --outcome / journal--> applied | refused | unknown
authorized --outcome, reconcile--> refused (no_commit_intent)
```

- **Commit intent** is refused with `push_settled` (any named entry is no longer in flight), `receive_expired` (deadline), `attempt_inactive` or, for a new intent, `repository_archived` (409; not in the route's contracted error list, but a known code the worker's client maps); repeating it for entries that already hold intent succeeds while the other conditions hold. The attempt's liveness is read first (a fast path), and the authoritative check runs in the intent's transaction after the record is locked: the grant row of the attempt is read `FOR UPDATE` through `Tx.Grants` (`gitauth.GrantByID`), and a cancellation revokes the attempt's grants in its own transaction (`gitauth.RevokeAttemptIn`), so the two serialize on that row: either the revocation committed first and the intent is refused, or the intent commits first and its transaction completes, as the specification allows. The deadline is checked again after the last lock (the grant row, and the repository row for a new intent) was acquired, immediately before the intent is saved, with the service's clock: a wait for a lock that crossed the deadline is `receive_expired` and changes nothing. This relies on T-150 revoking the grants in the cancelling transaction.
- **Outcome** applies the reported updates that reached `committing`, refuses entries that never did, refuses `committing` entries the report does not list (`receive_aborted`: post-receive lists exactly the refs Git updated, once, after the whole receive ended; the journal's `committed` entry cannot contradict it because Git runs the `committed` hook for every update of a batched transaction, including one it rejected), and treats an update reported applied without commit intent as `unknown` (`conflicting_evidence`); one reported applied that was already refused stays refused and is audited (`git.push.outcome_contradicted`). Audit rows and the one event commit with the entries; the event ID is fixed per record, so it is emitted when the record first becomes `applied` and never again. The event is `eventsv1.NewGitRefsUpdated` (count and kinds from the persisted kinds); its aggregate is the push record (`resource.type` `git_push`, `resource.id` the push ID, `resource.version` the record's version at settlement) and its payload names the repository.
- **Reconcile** reads evidence first and applies the decision in its own transaction, only to entries still in the state the evidence was read for. The evidence of one entry is one consistent snapshot: every head a worker reports is observed at once (the persisted known head, each page of the receive's journal and of the ref's journal, each value snapshot, quiescent or not), the highest survives failures and is persisted, and a head below the persisted one or below one already observed in the settlement is a regression that is latched: every committing entry of the settlement is `unknown` (`journal_regressed`) — decisions taken or waits begun before the regression was seen are replaced, and unknown is terminal (the database refuses any move out of it) — whatever the later reads show, and a value read whose journal head is beyond the journal read makes the journal be read again up to it (another transaction ran in between; a prepared entry on the ref then decides in place of the value). An own `committed` entry applies only if the ref agrees (the next prepared entry observed the new value, or the quiescent value is the new value); otherwise it is `conflicting_evidence` (`unknown`). An `authorized` entry is refused once the worker no longer runs the receive or the deadline passed; a `committing` entry is decided by `gitv1.Settle` (own committed or aborted entry, else the next prepared entry's `observed`, else the value under the lock once quiescent). A worker error of any outcome leaves the entry and is returned. A worker answer that its journal is unreadable (an error wrapping `ErrJournalUnreadable`, which the `Worker` adapter must produce only for that answer) waits and settles `unknown` (`journal_unreadable`) only after `Options.EvidenceTimeout` past the deadline; any other failure of a worker call (timeout, reset, no worker, a 503) is a transport failure that settles nothing, however long it lasts. The highest journal head seen is stored per repository and a lower head is `journal_regressed`.
- **Empty repositories.** A record whose applied entries made an empty repository non-empty records the obligation; it is reported to the repository module (`ReportEmpty(false, …)`) after the commit and repeated by `Reconcile` until it succeeds.
- **Unknown** entries are visible with a reason, emit nothing and block `UnknownBlocksWriter` (the `WriterGate` of the contract) for their ref. Reconciliation never resolves them; an administrator does, with `ResolveUnknown` (below, T-138).

## Operator actions (T-138)

- **Resolving an unknown entry.** `Service.ResolveUnknown` settles one `unknown` entry as `applied` or `refused` after an administrator inspected the repository. Order: scope and role (`Dependencies.Admin`, a `ResolveAuthorizer`; `forbidden`, a foreign repository or record is `not_found`), a reason (1 to 1024 bytes of text, required), then, in one transaction, the record locked, its version compared with `Expected` (`version_conflict`, the route's `If-Match`), the entry required to be still unknown (`push_settled` otherwise), the new state (`applied`; `refused` with reason `ref_unchanged`), a `git_push_resolutions` row (who, why and the value of the ref the control plane observed, read before the transaction and never a condition), an audit row `git.push.operator_resolved` plus the status audit row, and, when the record's status becomes `applied`, the one `git.refs_updated` event (deterministic identity per record, so it is exactly once whichever path settles the record). Resolving one of several unknown entries leaves the record unknown and emits nothing. When nothing unknown is left `UnknownBlocksWriter` and `UnsettledPush` clear. The database accepts the move out of `unknown` only when the resolution row of that entry and state was inserted in the same transaction (`txid`), so a plain `UPDATE` still cannot.
- **Route.** `POST …/repositories/{id}/pushes/{pushId}/resolutions` (`gitpushhttp.ActionResolve`, mounted only by `Handler.WithResolver`) with `If-Match: "<version>"` and `{"ref", "resolution", "reason"}`; `GET …/pushes/{pushId}` now sends the record's version as its `ETag`. The body type is `gitpushhttp.ResolveRequest` until T-158 lists the route in `api/git-pushes.yaml`.
- **Restore.** `Service.Settlement` reports a repository's in-flight and unknown entries and the known journal head; `Service.AcknowledgeRestore` lowers the known head to a restored volume's head, refused (`push_settled`) while any entry is in flight (the regression latch must first have made every committing entry unknown), recorded in `git_journal_resets` and the audit trail, and accepted by the database only with that row in the same transaction. Without it every later receive of a restored repository would read as a regression until its journal caught up. `internal/gitops` calls both.

- **Per-ref reads for the workspace.** `Service.UnsettledOnRef(scope, repositoryID, ref)` reports whether any push record of the repository has an entry for the ref that is `authorized`, `committing` or `unknown` (a push to the ref is in flight or its outcome is not known), and `Service.AppliedOnRef(scope, repositoryID, ref, limit)` returns up to `limit` (1 to `MaxAppliedOnRef`, 100) push records with an `applied` entry for the ref, newest first. They have the signatures of T-147's consumer-owned `RefPushes` port, which `*gitpush.Service` therefore satisfies; a foreign or unknown repository, or a repository of another project of the scope, is `not_found`, and a malformed ref `invalid_request`. **Apply order** is persisted per entry: the database numbers an entry (`git_push_entries.applied_seq`, from the monotone sequence `git_push_apply_seq`, by a trigger the runtime role cannot bypass) the moment it becomes `applied` (post-receive outcome, reconciliation or an operator resolution), and `AppliedOnRef` sorts by that number of the entry **for the asked ref**, newest first (ties by push ID descending); the memory store numbers the same way. A later change of the record (another of its entries settling) therefore does not move it, and a record whose entries applied at different times sorts by each ref's own apply. The number follows the order of the state-change statements, not of their commits. A database that already recorded applied entries before migration 015 gets them numbered by the migration (the record's last change, then push ID and ordinal) and the sequence continues after them (`Test_migration_015_backfills_apply_order`). `Tx.UnsettledOnRef` and `Tx.AppliedOnRef` are on the memory and PostgreSQL stores and run in the shared Contract; migration 015 adds the index on `(tenant_id, repository_id, ref, state)` of the entries they read.

## Persistence

`009_git_pushes.sql` owns the three tables with composite ownership keys to `repositories`, forced row level security on `kodama_tenant_id()`, check constraints that mirror `PushEntry.Validate` (kind against the values, a reason exactly for refused and unknown), guard triggers for the entry transition table, immutable identity, the version step and the monotone journal head (relaxed only for the operator actions by `015_git_operations.sql`: `git_push_resolutions` and `git_journal_resets`, insert-only, the guards read them by `txid`), and column-level grants (the runtime role never deletes and updates only state, reason, status, version and the report flag). A receive is unique per repository, so authorization is idempotent and two receives with identical `(ref, old, new)` tuples are two records.

## Open issues

- **T-128's journal records `committed` for a rejected ref.** Real Git runs the `reference-transaction committed` hook for every update of a batched (non-atomic) receive transaction, including one that failed (for example a directory/file ref conflict): the journal then says `committed` for a ref that does not exist (`partial_receive_lost_confirmation`). The reconciler contains it (the entry is `unknown`, never `applied`) and the post-receive report settles the common case correctly, but the worker should journal `committed` only for updates that took effect.

- The repository guard compares status, default branch, direct-push policy and hosting; a change of anything else (the name, the version) does not refuse a receive.
- The integration grant's "once" rests on Git's expected-old check (the same tuple cannot apply twice); the push authorizer does not additionally count receives per grant.
